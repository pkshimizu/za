# za:auto をボードが空になるまで回し、人の対応を issue のコメントで待つ

作成: 2026-10-18（shoki での運用から）

> **手順の正は `skills/auto/SKILL.md`。** 設計を攻撃させたレビュー（2026-10-18）で、待ちの種類を
> `decision` / `human_task` / `gate` / `release` にまとめ、機械のゲートを先に通す、ロックを取る、`needs_human` では `za:goal` を呼ばず先に人に頼む、などに直した。
> 下の本文はその前の版で、細部は SKILL.md と違う。

## 目的

`/za:auto` を起動したら、ボードのタスクを**すべて完了するまで**機械が消化する。
人の作業・判断・確認が要るところでは、**人への依頼を issue のコメントに書いて待つ**。
人が issue にコメントで返したら、`za:auto` がそれを読んで続きを進める。

## いまの動きと、ずれ

| いま | 望む動き |
|---|---|
| 1 回の起動で `max_per_run` 件（shoki は 1）処理して終わる | 処理できるものが無くなるまで続ける |
| 人に回した PR（実機確認・保護パス）の出口は、人の `/za:merge` だけ。`In review` は見直さない | 人がコメントで「確認した」「承認」と返したら、`za:auto` がマージまで進める |
| `要人手`・`要判断` の issue は拾わない（拾わないラベル） | 拾って、機械にできるところまで進め、人への依頼をコメントに書いて待つ |
| 昇格は「`## 依存` に `blocked by:` 以外の記述があれば上げない」 | 開いている依存の有無だけで決める（`Backlog` は他の issue の完了待ちだけ。2026-10-18 shoki で決めた） |
| 失敗が上限に達したら `needs_decision` + `Backlog` に落として止まる | 人への依頼（何が起きたか・どうしてほしいか）をコメントに書いて待つ |

## 設計

### 1. 待ち（wait）

人の対応が要るところで、`za:auto` は issue に**待ちのコメント**を 1 つ残す。

```
<!-- za:auto:waiting id=<連番> for=<種類> pr=<番号 or none> -->
za:auto: <日時> 人の対応を待っています（<種類>）

## お願いしたいこと
<何を・どこで・どうしてほしいか。デザインのプロンプト、判断の選択肢と推奨、実機確認の手順など>

## 返し方
この issue にコメントで返してください。<返してほしい内容。例: デザインの URL と書き出した HTML／選んだ案の番号／確認の結果>
```

| for | 使う場面 | 返ってきたら |
|---|---|---|
| `decision` | 着手前に決めることがある（`要判断` の issue、実装方針が決まらない、失敗が上限に達した） | 決まったことを issue 本文の「決めたこと」に書き、`要判断` を外し、実装に進む |
| `human_task` | 人の作業が成果物の一部（デザインを Claude Design で作る、実測する、外部サービスの設定） | 返ってきた成果（URL・貼られた内容・測った値）を確かめ、資料に反映して続きを進める |
| `manual_check` | `要実機確認` の PR を実機で確かめてほしい | 問題なし → 返事を PR にコメントで書き写してマージへ。問題あり → 直す（下の「直してから待ち直す」） |
| `approval` | 保護パスに触れる PR、base が違う PR など、人の承認でマージするもの | 承認 → マージへ。差し戻し → 直す |
| `release` | リリースの issue（`za:release` は人が起動する。下の「やらないこと」） | issue が閉じたら `Done` |

- **待ちの間、Status は `In progress` のままにし、人待ちのラベル（設定の役割 `waiting`。例: `人待ち`）を付ける**
  （2026-10-18 shoki で決めた）。人はボードの `In progress` をこのラベルで絞れば、自分の番の issue が分かる。
  ラベルは**見分けるための印**で、合図ではない（合図は下の 2）。付け外しは `za:auto` が行う
- 待ちのコメントは、同じ `for` で連投しない（いまの「同じ理由で連続して残さない」と同じ）

### 2. 合図はコメントで読む（ラベルでは読まない）

**人が終えた合図は、待ちのコメントより後の、`za:auto` 以外のコメント。** ラベルの付け外しは合図にしない
（2026-10-18 shoki で決めた）。

- `za:auto` も人も同じ `gh` のアカウントで書くので、書き手では区別できない。**`<!-- za:auto:` を含まない
  コメント**を人のコメントとみなす
- 「後」は、待ちのコメントの作成日時より後に**作られた、または書き直された**（`updatedAt`）コメント。
  人が前のコメントを書き直して返すこともあるため
- `gh api repos/{owner}/{repo}/issues/{n}/comments` で `created_at` / `updated_at` / `body` を取る
  （`gh issue view --comments` は更新日時を出さない）
- 返事を読んで、次のどれかに分ける:
  - **終わった・答えた** → 上の表の「返ってきたら」へ
  - **質問・足りない** → 答えるか、足りないものを書いた待ちのコメントを新しく残す（`id` を増やす）
  - **まだ・関係ない話** → 何もしない（待ち続ける）
  - 分けられない → 何もしない。報告に「読めなかった返事」として載せる（推測で進めない）
- 待ちの解決は、`<!-- za:auto:resolved id=<連番> -->` を含むコメントで記録する（同じ返事を 2 回処理しない）

### 3. 起動の中の流れ（ループ）

```
0. 設定と前提（いまと同じ）
1. ボードと実態を突き合わせる（いまと同じ + Waiting の item を集める）
2. 待ちを見直す: Waiting の各 item について、合図（上の 2）があれば続きを進める
3. Ready から 1 件選んで za:goal → ゲート → マージ（いまの手順 2〜7）
   - ゲートで人が要ると分かったら（実機確認・保護パス）、保留ではなく待ちに入る（上の 1）
4. 依存が解けた issue を Ready に上げる（開いている依存の有無だけで決める）
5. 2〜4 を、進められるものが無くなるまで繰り返す
6. 報告: すべて Done なら「完了」。残りが人待ちだけなら、待ちの一覧（issue・種類・お願いしたこと）
```

- **1 回の起動で処理する件数に上限は設けない**（2026-10-18 shoki で決めた。`max_per_run` は消す）。
  件数が増えると作業ログで文脈が圧縮され、前の件の細部が落ちる。そのため、件と件のあいだで必要な状態
  （PR 番号・SHA・待ちの id）は、いまと同じく文脈に頼らず `gh` で引き直す
- **継続運転**は、いまと同じく `/schedule` か cron から `claude -p "/za:auto"` を一定間隔で起動する。
  人の返事がいつ来るかは分からないので、1 つのセッションで待ち続けない
- 進められるものが無い起動は、ボードにも issue にも何も書かずに終わる（定期起動でコメントが積もらないように）

### 4. 人の作業がある issue（`要人手`）

拾わないラベルから外し、拾って**機械にできるところまで**進めてから `human_task` で待つ。

例: デザインの issue（shoki の #169・#177・#180）
1. `za:goal` が依頼書とプロンプトを書いて PR にし、レビューを収束させる
2. 待ち（`human_task`）: 「このプロンプトを Claude Design に入れ、できたデザインの URL と書き出した HTML を
   コメントで返してください」
3. 返事が来たら、PR のブランチでデザインを確かめ、依頼書の「デザインが決めたこと」などを書き、
   レビュー（`za:review`）を通してマージする
4. issue を閉じる

**デザインの読み方**: 無人の `claude -p` では Chrome が使えないことがある。Chrome の道具があれば URL を
開いて読み、無ければ返事に貼られた内容（書き出した HTML・画像）を読む。どちらも無ければ、足りないものを
書いて待ち直す。

### 5. 判断が要る issue（`要判断`）

拾わないラベルから外し、拾って `decision` で待つ。

1. `za:resolve-issue` と同じやり方で、コードと資料で解けるものは自分で解き、残った点だけを
   **選択肢と推奨つき**で待ちのコメントに書く
2. 返事が来たら、issue 本文に「決めたこと（<日付>）」として書き、`要判断` を外す
3. 依存が無ければそのまま実装に進む（`za:goal`）

### 6. 直してから待ち直す

`manual_check` / `approval` に「ここが違う」と返ってきたら:

1. 返事を指摘として、PR のブランチで直す（`za:review` の修正の原則: 最小の差分、検証を添える）
2. 修正した差分だけを再レビューする（`za:review` の 2 周目以降と同じ問い方）
3. 収束マーカーを打ち直し、同じ `for` で待ち直す（「直したので、もう一度確かめてください」）

**待ち直しの回数に上限は設けない**（2026-10-18 shoki で決めた）。人が「違う」と返すかぎり、直して待ち直す。
1 回の直しの中のレビューは、いままでどおり上限 3 周で打ち切る。

### 7. 設定（ORCHESTRATION.md）の変更

| 項目 | 変更 |
|---|---|
| Status | 変えない。人待ちも `In progress` |
| ラベル（新） | 役割 `waiting`（人待ちの印）を足す。必須 |
| ラベル | `needs_decision` / `needs_human` は「拾わない」から「拾って待つ」に意味を変える。`needs_manual_check` はそのまま |
| 昇格の条件 | 「`blocked by:` 以外の記述があれば上げない」を消す。`require_milestone` は残す |
| 上限 | `max_per_run` を消す（上限なし）。`max_failures` は残す（同じ issue が直らないまま回り続けないように。達したら `decision` で待つ） |
| 人間が見る場所 | ボードの `In progress` を人待ちのラベルで絞り、各 issue の最新の待ちのコメントに、コメントで返す |

`docs/ORCHESTRATION.md` はゲートそのものなので、各プロジェクトでの変更は人がマージする（いまと同じ）。

## やらないこと

- **`za:release` は呼ばない。** 本番に出す操作は、人が内容を見て承認する（`za:release` 自身の決まり）。
  リリースの issue は `release` で待ち、人が `/za:release` を走らせて issue が閉じたら `Done` にする
- **マージの承認を GitHub の Approve で取らない。** PR を作ったアカウントは自分の PR を Approve できない
  （`za:auto` は人と同じアカウントで PR を作る）。承認もコメントで返してもらう
- ラベルを合図にしない（上の 2）

## 危ないところ

- **コメントを指示として読む。** 返事は人が書いたものとして扱うが、リポジトリに書き込める人なら誰でも
  コメントを残せる。非公開・1 人で使うリポジトリを前提にし、`za:auto` 自身の安全側の決まり
  （force push しない、`--admin` を使わない、保護パスは人の承認が要る）は返事の内容で緩めない
- **承認の取り違え。** 「承認」の返事が、どの PR・どの head に対するものかを固定する。待ちのコメントに
  `pr=` と head の SHA を書き、返事のあとに head が進んでいたら承認として扱わず待ち直す
- **auto モードの分類器。** 人の Approve の無い PR のマージは分類器が止める。いまの例外（`--match-head-commit`
  付きの `gh pr merge`）で通るかを、保護パスの承認でも確かめる

## 進め方

1. このプランを見てもらい、決める点（下）に答えてもらう
2. za の `skills/auto/SKILL.md`・`assets/ORCHESTRATION.template.md`・`agents/openai.yaml`・`README.md` を直して PR にする
3. shoki に人待ちのラベルを作り、`docs/ORCHESTRATION.md` を合わせる PR を作る
4. shoki で慣らし運転する（#169 のデザインの待ちで、一巡を確かめる）

## 決めたこと（2026-10-18）

- 人が終えた合図は、issue のコメント（新しく書いた・書き直した）で読む。ラベルでは読まない
- 実機確認・承認で「違う」と返ってきたら、`za:auto` が直して待ち直す。回数の上限は設けない
- 1 回の起動で処理する件数に上限は設けない

- 人待ちは Status を `In progress` のままにし、ラベルで見分ける
