# za:review — PR を観点別に並列レビューして修正

GitHub プルリクエスト（PR）を、プロジェクトが定めたレビュー観点ごとに**並列で**レビューし、
出た指摘を修正し、再レビューする。1 周目は全重要度を対象に、2 周目以降は前の周の指摘の解消と
新しい blocker だけを対象に、上限 3 周で収束させる。狙いは、観点を分担させて網羅的かつ素早く
レビューし、その場で直し切ること。そしてレビューで得た知見をルールとして蓄積し、同じ指摘が
二度出ないようにすること。修正は最小の差分にとどめ、2 周目以降は修正した差分だけを問うことで、
修正が次の周の指摘を生む往復を止める。

下の手順を順番に実行する。周ごとに修正をコミットし、収束したら**リモートへ push する**
（PR に追従させる）。

ユーザーに質問・確認を求めるときは、原則 `AskUserQuestion` で**選択式**（推奨できる案を
先頭の選択肢に置き、必要に応じて「おまかせ」などの選択肢を添える）で尋ねる。はい/いいえの
承認も含め、自由記述でしか答えられないものを除いて選択肢で提示する。

## 手順

### 1. 対象 PR を特定してチェックアウトする

レビュー対象は、**このスキルに渡された引数の PR 番号/URL** から特定する
（例: `/za:review 42`）。

- 引数が無い場合: `gh pr list` を提示し、「どの PR をレビューしますか？」と確認する。
- `gh pr view <番号>`（必要なら `--comments`）と `gh pr diff <番号>` で内容と差分を把握する。
- 修正を加えるため、`gh pr checkout <番号>` で PR のブランチをローカルに取り出す。
  作業ツリーに未コミットの変更があれば、混ざらないよう先に確認する。
- PR が見つからない／クローズ済み、`gh` が使えない場合は、推測で進めず状況を伝えて確認する。

### 2. レビュー観点を読み込む

`docs/review-perspectives/` 配下の `*.md` が、それぞれ 1 つのレビュー観点
（例: `security.md`, `readability.md`, `tests.md`）で、何をどう見るかが書かれている。
レビューはこの観点に沿って行う（プロジェクトが観点の所有者）。

ただし**全部は読まない**。この PR の差分に関係しない観点まで読み込むのは、そのまま
無駄なエージェント起動につながる。**索引を先に読み、対象になりうる観点だけを開く。**

#### 2-a. 索引を読む

`docs/review-perspectives/INDEX.md` を読む。1 行 1 観点ファイルの索引で、次の形式:

```markdown
- `security.md` — 認証・入力検証・秘匿情報の扱い | paths: `api/**`, `auth/**` | model: opus
- `readability.md` — 命名・構造・可読性 | 適用: 常に
- `tests.md` — テストの有無と質 | paths: `**/*_test.go`, `tests/**`
```

- `paths` がある行は、**ファイルを開かずに**手順 3-a の差分ルーティング判定に使える。
- `適用: 常に`（または `paths` なし）の行は常に対象。
- `model` は、その観点のサブエージェントに使うモデル（省略時はこのスキルと同じ）。

観点ファイル自身も、先頭に同じ意味の frontmatter を持てる（**すべて任意**）:

```yaml
---
paths:              # この観点が担当する変更のパス（glob）。省略時は常に対象
  - "api/**"
exclude:            # 任意。paths に当たっても除外するパス
  - "docs/plans/**"
model: sonnet       # 任意。この観点のサブエージェントに使うモデル。省略時はこのスキルと同じ
---
```

索引と frontmatter が食い違った場合は、**読み込んだファイルの frontmatter を正**とする
（ルールの本体はファイル側にあるため）。食い違いに気づいたら、索引を直すことを提案する。

#### 索引が無い・ずれている場合

- `INDEX.md` が無い場合: 配下の `*.md` を**すべて**読み込み、frontmatter で判定する
  （従来どおりの挙動）。そのうえで、次回以降のために `/za:index` で索引を作ることを提案する。
- 索引に載っていないファイルがある場合: **その観点は対象として扱う**（更新漏れでレビューが
  素通りするのを防ぐ）。そのうえで索引への追記を提案する。
- 索引にあるファイルが実在しない場合: その行が古いことを報告し、索引の修正を提案する。
- ディレクトリやファイルが無い場合: 「`docs/review-perspectives/` が無いため、標準観点で
  レビューします」と伝え、末尾の**「デフォルトのレビュー観点」**を使う。

### 3. 観点ごとに並列でレビューする

#### 3-a. 起動する観点を選ぶ（差分ルーティング）

`gh pr diff <番号> --name-only` で変更ファイルの一覧を取得し、**索引の各行**について
対象かを判定する（判定材料は索引の `paths` / `exclude`。索引に無い観点はファイルの
frontmatter を見る）:

- `paths` を持つ観点: 変更ファイルのうち `paths` のいずれかに一致し、かつ `exclude` の
  いずれにも一致しないものが 1 つ以上あれば**対象**。1 つも無ければ**起動しない**。
- `paths` を持たない観点: 常に対象。

対象になった観点のファイルだけを読み込む（ここで初めて開く）。読んだ frontmatter が索引と
食い違っていて対象外と分かった場合は、そこで落として索引の修正を提案する。

観点ファイルの本文にも「対象ファイルが差分に無い場合は指摘なしと返す」と書かれていることが
あるが、それは**エージェントを起動してから**判定する書き方で、1 エージェントを丸ごと無駄に
する。ここで**起動前に**落とす。

- 対象外にした観点は、名前だけを一覧で示す（何を見ていないかが分かるようにするため）。
- 判定の結果**対象が 0 件になった場合は、`paths` を無視して全観点を起動する**。差分の置き場所が
  想定外だったときに、レビューが丸ごと素通りするのを防ぐ。

#### 3-b. 選んだ観点を並列でレビューする

3-a で対象となった観点ごとに**サブエージェントを 1 つ起動し、すべて並列で実行する**
（同時に投げて待つ）。観点を分担させることで、各エージェントが 1 つの視点に集中でき、
レビューが深く・速くなる。

各エージェントには次を渡す:

- 担当する観点ファイルの内容（その観点の見方）
- PR の差分（`gh pr diff` の結果）と、必要に応じてリポジトリを読む指示
  （差分だけでは文脈が足りないことがあるため、周辺コードの参照を許可する）
- 出力形式（下記「指摘の形式」）

サブエージェントのモデルは、観点の frontmatter の `model` に従う（未指定ならこのスキルと
同じモデル）。観点によって求められる判断の重さが違うため、プロジェクトが観点ごとに指定できる
ようにしてある。

各エージェントは、その観点での指摘の一覧を構造化して返す。指摘が無ければ「指摘なし」を返す。

### 4. 指摘を集約して修正する

全エージェントの指摘を集約し、重複をまとめ、重要度順に整理して**通し番号を振る**（再レビューで
解消判定を照合するキーになる）。各指摘について**対応するか否かを判断**する:

- **blocker / major は必須**で直す。例外は、誤検知・スコープ外・設計上の意図・トレードオフと
  判断した場合だけ（理由を記録する。サマリーの「対応しなかった指摘」に載る）。観点間で矛盾する
  指摘があれば、プロジェクトの方針（観点ファイル・既存コード・ADR 等）に照らして優先順位を
  決め、判断の根拠を残す。
- **minor / nit は任意**。その場で最小の差分で直せるものだけ直し、直さないものは
  **「記録のみ」**にする。**issue にはしない**。同じ minor / nit が繰り返し出るなら、手順 8 で
  ルール化して指摘そのものが出ないようにする（個別に直し続けるより、そのほうが安い）。

用語（このスキル全体で同じ意味で使う）:

- **記録のみ**: 重要度にかかわらず、この周では直さず理由を 1 行残すもの。行き先は 3 通り。
  minor / nit → issue にしない（繰り返すならルール化）。設計変更 → **持ち越す**（下記）。
  2 周目以降に出た blocker 以外の新規指摘 → 収束後にまとめて提示し、ユーザーが issue 化を選べる。
- **持ち越す**: 設計変更を、この PR とは独立した変更（別 issue）に送ること。issue にする
  （`za:fix-issue` の「着手前に設計を叩く」の対象になる）。
- **繰り越す**: 未解消 / 悪化と判定された指摘を、同じ番号のまま次の周に残すこと。

#### 修正は指摘された箇所だけを直す最小の差分にする

再レビューが収束しない最大の原因は、**レビュー修正が新しい未レビューのコードを生み、それが
次の周の指摘対象になる**こと。レビュー修正は前の周の修正と同じファイル・同じ行に集中するので、
重要度や観点で絞るだけでは止まらない。修正の作り方で止める:

- **指摘された箇所だけを、最小の差分で直す。** 周辺を「ついでに」整えない。
- **設計を変える修正（書き直し・リファクタ・構造の変更・ヘルパーの抽出）は、その周では
  行わない。** minor の指摘に対して判定ロジックを書き直すと、次の周の major はその新しい
  関数に対する指摘になる。設計変更が必要なら記録のみにして持ち越す。blocker / major でも
  同じで、最小の修正で塞げないなら、いったん塞ぎ方だけを直し（これが「対応した」）、設計変更は
  持ち越す。
- **修正には検証を添える。** 次の 3 通りで、どれに当たるかを修正ごとに記録する:
  1. テスト基盤があり、テストで表せる → 直す前に落ちて直した後に通るテストを付ける。実装を
     わざと壊して落ちることまで確かめる。**テスト名・実行コマンド・落ちたときの出力**を記録
     できたものだけを「検証済み」と呼ぶ（宣言だけでは検証済みにならない）。
  2. テスト基盤が無い、またはテストで表せない（文言・doc・設定・Markdown）→ 何をどう確かめたか
     （実行したコマンド、読み直した箇所、再現手順）を 1 行記録する。検証済みとは呼ばない。
  3. テスト基盤の新設が要る → その周ではやらず、設計変更と同じく持ち越す。

#### 修正したら、機械で取れるものは機械で掃く

修正を終えたら、**次の周を待たずに**その場で掃き出す。ここで取れる指摘が次の周へ流れると、
1 周（十数分）を丸ごと消費して「参照が古い」と言われるだけになる。エージェントを増やさず
grep で済むので、必ずやる:

- **削除・改名した識別子への参照**（関数・型・定数・テスト名）。コードだけでなく
  **doc コメント・`docs/`・README** も対象。`grep -rn '<旧名>'` が 0 件になるまで。
- **挙動を変えた箇所の古い記述**。「必ず〜する」「〜しない」と書いてある doc が、変更後も
  正しいかを読み直す。とくに**変更した関数を指している他ファイルの記述**は差分に出ないので
  見落としやすい。
- **前方参照**（「後続 #NN で対応」など）。その issue を実装したなら消す。
- プロジェクトのルールにある機械的な検査（文言の言語、フォーマッタ、リンタ）。

#### 周ごとにコミットする

掃き終えたら、**その周の修正を 1 つのコミットにまとめてコミットする**（再レビューの前に）。
次の周に渡す差分と、上限のカウントがこのコミットを基準にするため。

- コミット規約が `docs/COMMIT.md` / `docs/ISSUE.md` / `docs/rules/` にあればそれに従う。
  無ければ、レビュー対応で何を直したかが分かる簡潔なメッセージにする。
- 規約にかかわらず、メッセージ本文に **`review-round: N`**（N は周番号）の行を必ず入れる。
  上限の判定はこの行を機械的に数える（手順 5）。
- 手順 8 のルール化（繰り返しそうな指摘を `docs/rules/` へ）は、**この時点（コミット前）で**
  行い、同じ周のコミットに含める。

### 5. 再レビューして収束させる

もう一度レビューする。ただし 2 周目以降は、1 周目と**問い方を変える**。変えるのは**渡す差分の
範囲**と**受け付ける指摘の範囲**（理由は手順 4 の冒頭）。観点ファイルは引き続き渡すが、役割は
重大度の判定基準に限る。観点やファイル一致で絞る手順 3-a は、2 周目以降には効かない（修正は
前の周と同じファイルに当たるので、同じ観点が選ばれる）。

| 変える点 | 1 周目 | 2 周目以降 |
|---|---|---|
| 渡す差分 | PR 全体 | **前の周で直した差分だけ**（周のコミットは 1 つなので `git show HEAD`。HEAD がその周の `review-round:` コミットであることを確認する） |
| 併せて渡すもの | なし | 前の周の指摘（番号つき）と、それぞれをどう直し、どの検証（手順 4 の 1〜3）を添えたか |
| 出してよい指摘 | 全重要度 | **前の周の指摘ごとの解消判定**（解消 / 未解消 / 悪化）と、修正が生んだコードの**新しい blocker だけ** |
| それ以外 | — | 「記録のみ」として 1 行。直す対象にしない |

2 周目以降のエージェントに渡すもの（手順 3-b に相当）:

- 担当する観点ファイルの内容（重大度の判定基準として）
- 上の表の差分と、前の周の指摘一覧（番号・場所・指摘・どう直したか・検証の種類と記録）
- 「対応しない」と判断済みの指摘（番号と理由）。再度指摘させない
- 「前の周の修正は新しい穴を作ることがある（とくに並行性・状態機械）。**その修正自体が生んだ
  問題**を探せ」という指示。検証済み（手順 4 の 1）の修正は、指摘そのものの再発確認は省いて
  よいが、差分は渡し、その修正が別の場所に作った問題は探させる
- 読む範囲: 修正箇所の周辺だけ。PR 全体の見直しはしない
- 出力形式（末尾「2 周目以降の指摘の形式」）。**新しい blocker には再現手順か落ちるテストを
  必須にする**。書けないものは報告させない（「気になる」程度の指摘で周を増やさない）

判定の扱い:

- **解消** → 閉じる。
- **未解消** → 同じ番号で繰り越す。最小の差分で直し直す（手順 4 に戻る。最終周を除く）。
  新しい blocker も同様に手順 4 で直す。「戻す（revert）」は周コミットの `git revert` ではなく、
  該当箇所だけを手で戻すこと（周コミットは複数の修正を束ねているため）。
- **悪化** → 前の周の修正が原因なので、同じ場所をさらに直さない。**まず前の周の修正を戻す
  （revert）ことを第一候補**にする。戻したあとの元の指摘の扱いは重要度で決める:
  blocker / major は同じ番号で繰り越し、最小の差分で直し直す（設計変更が要るなら塞ぎ方だけ
  直して設計変更は持ち越す）。minor / nit は記録のみにする。戻した事実と理由は、その指摘の
  備考としてサマリーに載せる。
- 「対応しない」と判断済みの指摘、記録のみの指摘は、解消判定の対象に**含めない**（含めると
  定義上収束しない）。再度出ても蒸し返さない。

**再レビューするエージェント**: 1 観点 1 エージェントは保たない。前の周で**対応した指摘を
出した観点**と、修正で新たに触ったファイルが 3-a の判定で当たる観点をまとめて 1〜2 エージェント
に束ね、上の内容を渡す（待ち時間は最も遅いエージェントで決まり、2 周目以降の担当範囲は小さい
ため）。非対応・記録のみしか出さなかった観点は再実行しない（見る修正が無い）。束ねたときは、
出力に**どの観点からの指摘か**を書かせる（サマリーで観点別に並べるため）。

**収束と上限**:

- 繰り越した指摘がすべて「解消」で、新しい blocker が無ければ**収束**。
- 上限は **3 周**（初回 + 再レビュー 2 周）。周は手順 4 のコミットで数える:
  `git log <PR の base>..HEAD --grep='^review-round:' --oneline | wc -l`。
  この値が **2 の状態で行う再レビューが最終周（3 周目）**。最終周で未解消 / 悪化 / 新しい
  blocker が出ても**手順 4 に戻らず**（直さず・コミットせず）、下の報告に進む。値が 3 以上
  なら（同じ PR で再実行した場合など）再レビュー自体をせず、その旨を伝えて下の報告に進む。
  自己申告で数えない。「あと 1 周だけ」は認めない。
- 最終周で収束しなかった場合は、まず手順 6 の push を行い（ここまでの修正は失わない）、
  **残っている指摘（未解消 / 悪化 / 新しい blocker）を一覧でユーザーに報告し、直すか issue 化
  するかを確認する**。記録のみの指摘も一覧に添える（issue 化は minor / nit を除く）。黙って
  続けない・黙って切らない。ユーザーが「直す」を選んだものは、**周を増やさず**最小の差分と
  検証で直し、`review-round:` を**付けない**コミットにして push し、サマリーに「打ち切り後の
  修正（未レビュー）」と明記する。再レビューが要る規模なら直さず issue 化する。
  `za:goal` / `za:cross-goal` 経由では push と報告までで停止するので、この確認には至らない。

### 6. push する

収束（または打ち切り）したら、`git status` で未コミットの変更が無いことを確認し、`git push` で
リモートへ反映する（PR の head ブランチに追従させ、レビュー指摘の修正を PR 上で確認できるように
する）。upstream が未設定なら `git push -u origin <ブランチ>`。push に失敗した場合（リモートが
先行している等）は状況を報告し、強制 push は勝手に行わない。

### 7. 修正内容のサマリーを表示する

次を表示する:

- **レビュー範囲**: 起動した観点 / 差分に当たらず**対象外にした観点**（名前だけでよい）と、
  何周回って収束したか（打ち切った場合はその旨とユーザー確認の結果）
- **修正内容のサマリー**: 何を直したか（ファイル単位の要点）と、検証済み（手順 4 の 1）に
  できた修正の割合
- **指摘の一覧**: 1 つの表にまとめ、状態列で区別する。番号 / 観点 / 指摘 / 状態 / 備考。
  状態は次のいずれか（排他）:
  - **対応**: 直した（どう直したか・検証を備考に）
  - **非対応**: 誤検知・スコープ外・設計上の意図・トレードオフ（理由を備考に）
  - **記録のみ**: 直さなかった minor / nit、2 周目以降の blocker 以外、持ち越した設計変更
    （行き先を備考に）
  - **未解消**: 打ち切り時に未解消 / 悪化 / 新しい blocker のまま残ったもの
- **push 結果**: コミットして push したブランチ（PR への反映）

### 8. 繰り返しそうな指摘をルール化する

今回の指摘のうち、**今後も繰り返し指摘される可能性が高いもの**（プロジェクト共通の規約・
落とし穴）を `docs/rules/{name}.md` に追記・修正する。`{name}` は内容に合った分類
（例: `naming.md`, `error-handling.md`）。既存の近いルールがあればそこへ追記し、無ければ
新規作成する。これにより `za:fix-issue` など他の作業が同じルールを参照でき、同種の指摘が
減っていく。

- **新しいルールファイルを作った場合は、`docs/rules/INDEX.md` にも 1 行追記する**
  （要約と適用条件）。索引に載らないルールは `za:fix-issue` の選別で「索引漏れ」として
  毎回読まれることになり、絞り込みの意味が薄れる。既存ファイルへの追記でも、適用条件が
  変わったなら索引の行を直す。
- ルール化の作業は**各周の手順 4（コミット前）で行い**、同じ周のコミットに含める。収束後に
  気づいたものは `review-round:` を付けない別コミットにして push する。何を追加・修正したかを
  サマリーで報告する。

## 指摘の形式

1 周目の各レビューエージェントは、指摘を次の形式で返す:

```
- 重要度: blocker | major | minor | nit
  場所: <ファイルパス>:<行>
  指摘: <何が問題か>
  根拠: <なぜ問題か。観点ファイルや規約・一般原則への参照>
  提案: <どう直すか>
```

## 2 周目以降の指摘の形式

2 周目以降のエージェントは、前の周の指摘ごとの判定と、新しい blocker だけを返す:

```
- 判定: #<前の周の番号> → 解消 | 未解消 | 悪化
  根拠: <1〜2 行。未解消 / 悪化なら、何がどう残っている・悪くなったか>

- 新しい blocker
  観点: <どの観点からか>
  場所: <ファイルパス>:<行>
  指摘: <何が問題か>
  再現: <再現手順、または落ちるテスト。書けなければこの指摘は出さない>
  提案: <どう直すか>

- 記録のみ: <1 行。直す対象にしない>
```

## デフォルトのレビュー観点

`docs/review-perspectives/` が無い場合に使う標準観点。これらを並列エージェントの担当とする:

- **正確性/バグ**: ロジック誤り、境界条件、null/例外、競合、後方互換性
- **可読性/保守性**: 命名、責務分離、重複、過度な複雑さ、既存コードとの一貫性
- **テスト**: 変更に対するテストの有無・妥当性、抜けているケース
- **セキュリティ**: 入力検証、認可、機微情報の扱い、インジェクション
- **パフォーマンス**: 不要な計算・I/O、N+1、明らかな非効率
