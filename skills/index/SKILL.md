# za:index — ルール／観点の索引を作る

`za:fix-issue` は `docs/rules/` を、`za:review` は `docs/review-perspectives/` を読むが、
どちらも**全ファイルは読まない**。先頭で `INDEX.md` を読み、今回の実装・差分に関係する
ファイルだけを開く。このスキルはその `INDEX.md` を、既存のファイル群から生成する。

索引を作るときだけは全ファイルを読む。**以降の毎回の読み込みを減らすための一度きりの投資**
であり、ここでの読み漏れは以後ずっと効くので、調査は丁寧に行う。

ユーザーに質問・確認を求めるときは、原則 `AskUserQuestion` で**選択式**（推奨できる案を
先頭の選択肢に置き、必要に応じて「おまかせ」などの選択肢を添える）で尋ねる。はい/いいえの
承認も含め、自由記述でしか答えられないものを除いて選択肢で提示する。

## 手順

### 1. 対象ディレクトリを確認する

`docs/rules/` と `docs/review-perspectives/` の有無を確認し、**存在するものだけ**を対象にする
（片方しか無ければそれだけ作る）。

- どちらも無い場合: 索引を作る対象が無い。その旨を伝えて止まる（空のディレクトリや
  ひな形を勝手に作らない）。
- 引数でディレクトリが指定された場合（例: `/za:index docs/rules`）は、それだけを対象にする。
- 既に `INDEX.md` がある場合は**上書きしない**。手順 5 で差分を提示して確認する。

### 2. 対象ファイルをすべて読む

各ディレクトリ配下の `*.md`（`INDEX.md` 自身は除く）を**すべて**読む。あわせて、パスの
妥当性を判断するためにリポジトリのディレクトリ構成も把握する（`git ls-files` の上位階層など）。

### 3. ファイルごとに索引の 1 行を組み立てる

各ファイルについて次を決める:

- **要約**: 何を規定しているかを 1 行（20〜40 字程度）。**ファイル名の言い換えにしない**。
  中身を読まないと分からない情報を書く（索引の価値はここにしかない）。
- **適用条件**: どんなときに読む必要があるか。
  - 実装・差分の内容に依らず常に効くもの（命名、コミット規約、全体のスタイル等）→ `適用: 常に`
  - 特定の領域にだけ効くもの → その領域を **リポジトリに実在するパスの glob** で書く。
- **model**（`docs/review-perspectives/` のみ・任意）: 既存 frontmatter に `model` があれば転記する。
  無ければ**書かない**（勝手に決めない）。

判断の指針:

- ファイル先頭に frontmatter（`paths` / `exclude` / `model`）がある場合は、**それを正**として
  転記する。自分の読み取りと食い違う場合は frontmatter を優先し、食い違った点を報告する。
- **迷ったら `適用: 常に` に倒す**。読みすぎは文脈が少し膨らむだけだが、読み落としは規約違反の
  実装やレビュー漏れになる。**コストが非対称なので安全側に寄せる。**
- `paths` を書くときは、その glob に**実際にファイルが存在することを確認する**。存在しない
  glob を書くと、その観点は以後永久に起動しない（静かに素通りするので気づけない）。

### 4. 索引を書き出す

形式は 1 行 1 ファイル。**折り返さない**（1 ファイルが複数行になると、機械的に読むときに
行とファイルの対応が崩れる）。

`docs/rules/INDEX.md`:

```markdown
# 実装ルールの索引

za:fix-issue / za:hunk-resolve が最初に読む索引。1 行 1 ファイル。
ルールを追加・変更したら、この索引も更新すること。

- `naming.md` — 変数・関数・ファイルの命名規約 | 適用: 常に
- `commit.md` — コミットメッセージの書式と粒度 | 適用: 常に
- `testing.md` — テストの粒度・命名・モックの方針 | 適用: テストを追加・変更するとき
- `api-design.md` — REST エンドポイントの設計とエラー表現 | 適用: `src/api/**` を触るとき
```

`docs/review-perspectives/INDEX.md`:

```markdown
# レビュー観点の索引

za:review / za:cross-review が最初に読む索引。1 行 1 ファイル。
`paths` があるものは、ファイルを開かずに差分ルーティング判定に使われる。
観点を追加・変更したら、この索引も更新すること。

- `readability.md` — 命名・構造・可読性 | 適用: 常に
- `security.md` — 認証・入力検証・秘匿情報の扱い | paths: `src/api/**`, `src/auth/**`
- `tests.md` — テストの有無と質 | paths: `**/*.test.ts`, `tests/**`
- `sql.md` — クエリの正確性と N+1 | paths: `src/db/**` | exclude: `src/db/migrations/**`
```

索引には**選別のための情報だけ**を持たせる。ルールや観点の中身をここに書き写さない
（二重管理になり、必ずずれる）。

### 5. 既存の索引がある場合

上書きせず、**既存の索引と新しく組み立てた内容の差分**を提示する:

- 索引に無い新しいファイル（追記が要る）
- 索引にあるが実在しないファイル（行の削除が要る）
- 要約・適用条件が変わったファイル

そのうえで「差分だけ反映するか／全面的に作り直すか／やめるか」を確認する。既存の索引は
人手で調整されていることがあるため、勝手に潰さない。

### 6. 完了報告

次を報告する:

- 作成・更新した `INDEX.md` のパスと、載せたファイル数
- `適用: 常に` にしたファイルと、そう判断した根拠
- パスを絞ったファイルと、割り当てた glob
- **判断に迷ったファイル**（どちらとも取れるもの）。手順 3 のとおり `適用: 常に` 側に倒して
  あるので、「絞り込める可能性あり」として名前を挙げる。実際に絞るかはユーザーが決める。

## 補足

- 索引はルール・観点を**追加したときに更新するもの**。`za:review` の手順 8 で新しいルールを
  作った場合は、その場で `docs/rules/INDEX.md` に 1 行追記される。このスキルは、
  索引がまだ無い既存プロジェクトへの導入と、更新が滞って古くなったときの作り直しに使う。
- 索引が無い場合、`za:fix-issue` / `za:review` は全ファイル読み込みへ縮退する。動きはするので、
  索引作成は**必須ではなく最適化**。ファイル数が少ないうちは作らなくてよい。
