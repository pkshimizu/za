# za:fix-issue — issue を実装してコミット

GitHub issue を起点に、プロジェクトのルールに沿って実装し、専用ブランチでコミットする
ところまでを一気通貫で行う。狙いは、issue に書かれた意図を正しく実装に落とし、
作業を追跡可能なブランチ単位に切り分けること。

下の手順を順番に実行する。コミットはするが、**push や PR 作成まではしない**
（そこは別の作業）。

ユーザーに質問・確認を求めるときは、原則 `AskUserQuestion` で**選択式**（推奨できる案を
先頭の選択肢に置き、必要に応じて「おまかせ」などの選択肢を添える）で尋ねる。はい/いいえの
承認も含め、自由記述でしか答えられないものを除いて選択肢で提示する。

## 手順

### 1. 対象の issue を取得する

実装対象は、**このスキルに渡された引数の issue 番号**から特定する
（例: `/za:fix-issue 42`）。`gh issue view <番号>`（必要なら `--comments`）で、
タイトル・本文・コメント・ラベルを取得し、何を作るのかを把握する。

- 引数が無い場合: `gh issue list`（オープンな issue、必要なら自分担当 `--assignee @me`）を
  提示し、「どの issue を対応しますか？」とユーザーに確認する。
- 番号の issue が見つからない／クローズ済みの場合: 推測で別の issue を実装せず、
  状況を伝えて確認する。
- リポジトリが git でない、`gh` で issue を取得できない場合も、その旨を伝えて確認する。

### 2. 実装ルールを読む

`docs/rules/` は、コーディング規約・命名・テスト方針・コミット規約など、このプロジェクトで
実装が従うべきルールの置き場。実装とコミットは必ずこれに従う（プロジェクトがルールの
所有者であり、こちらが我流を持ち込まない）。

ただし**全部は読まない**。ルールが増えるほど、今回の issue に関係しないルール
（触らない層の規約、使わない言語の規約）まで読み込むことになり、肝心のルールが埋もれる。
**索引を先に読み、今回の実装に関係するものだけを開く。**

#### 2-a. 索引を読む

`docs/rules/INDEX.md` を読む。これは 1 行 1 ルールファイルの索引で、次の形式:

```markdown
- `naming.md` — 変数・関数・ファイルの命名規約 | 適用: 常に
- `testing.md` — テストの粒度と書き方 | 適用: テストを追加・変更するとき
- `api-design.md` — REST エンドポイントの設計方針 | 適用: `api/**` を触るとき
```

- `適用: 常に` のものは、issue の内容にかかわらず必ず読む（コミット規約など、
  実装の中身に依らず効くルールがここに来る）。
- それ以外は、**issue の内容（何を作るか・どのファイルを触りそうか）と適用条件を
  突き合わせて**、関係するものだけを選ぶ。
- **迷ったら読む**。読みすぎのコストは文脈が少し膨らむだけだが、読み落としは規約違反の
  実装になり、レビューで 1 周増える。**非対称なので安全側に倒す。**
- 選んだファイルと、**選ばなかったファイル（名前だけ）**をユーザーに示す。何を見ていないかが
  分かるようにするため。

#### 2-b. 選んだルールを読む

選んだ `docs/rules/*.md` を読み込む。実装中に「このルールが要る」と気づいた場合は、
その時点で追加で読んでよい（索引の選択に縛られない）。

#### 索引が無い・ずれている場合

- `INDEX.md` が無い場合: `docs/rules/` 配下の `*.md` を**すべて**読み込む（従来どおりの挙動）。
  そのうえで、次回以降のために索引を作ることを提案する（作成は承認を得てから）。
- 索引に載っていないファイルが `docs/rules/` にある場合: **そのファイルは読む**
  （索引の更新漏れで規約が素通りするのを防ぐ）。そのうえで索引への追記を提案する。
- 索引にあるファイルが実在しない場合: その行が古いことを報告し、索引の修正を提案する。
- ディレクトリやファイルが無い場合: 「`docs/rules/` が無いため、既存コードの流儀に
  合わせて実装します」と伝え、リポジトリの既存コードの規約（命名・構成・テストの書き方）を
  読み取って準拠する。

### 3. 作業ブランチを作成する

`feature/{issue番号}-{title}` の名前でブランチを切る。

- `{title}`: issue タイトルから作る短い kebab-case スラッグ（小文字英数字とハイフン）。
  タイトルが日本語の場合は、要点を表す短い英語スラッグにする（例: 「ログイン機能の追加」→
  `add-login`）。長すぎる場合は要点だけに切り詰める。
- 切る前に作業ツリーの状態を確認する（`git status`）。未コミットの変更があれば、
  混ざらないようユーザーに確認する。
- 分岐元は原則として最新のデフォルトブランチ（`main` 等）にする。必要なら先に
  `git switch main` → 最新化してから分岐する。
- ただし **現在のブランチがデフォルトブランチでない場合**は、勝手に分岐元を決めず
  ユーザーに確認する。「現在のブランチ（`{現在のブランチ名}`）から分岐するか、デフォルト
  ブランチ（`{デフォルトブランチ名}`）に切り替えてから分岐するか」を提示し、選ばせる
  （`AskUserQuestion` 等）。スタックした作業（前の feature ブランチの続き）では現在ブランチ
  からの分岐が正しいこともあるため、ここを取り違えると余計なコミットが混ざる。

### 4. 実装する

issue の内容に従って実装する。進め方の指針:

- まず issue から「達成すべき振る舞い・受け入れ条件」を読み取り、影響範囲を把握する
  （関連コードを読む）。issue の記述が曖昧、または大きくて判断が要る場合は、着手前に
  実装方針を一言ユーザーに確認する。
- ステップ2で読んだルールと既存コードの流儀に沿って書く。
- テストがあるプロジェクトなら、関連するテストを追加・更新し、実行して通す。
  ビルド/型チェックがあれば通るところまで確認する。
- issue の受け入れ条件を一つずつ満たしているか確認する。

#### 着手前に設計を 1 回叩く（該当する issue のみ）

次のどれかに当てはまる issue は、**コードを書き始める前に**設計を短く固め、サブエージェント
1 つに**敵対的に攻撃させて**から実装する:

- 共有された可変状態・ロック・スレッド間の同期が絡む
- 状態機械（enum の遷移）や、コード全体で守るべき不変条件を新しく作る
- 「ある操作が別の操作を打ち消す／中断する」たぐいのキャンセル・打ち切り機構

理由は、この種の変更が**指摘 → 直す → その修正が次の穴を作る**という往復を招き、レビューの
周回数がそのまま伸びるため。設計段階なら 1 エージェント・数分で潰せる穴が、実装後だと
1 周（十数分）かかる。

やり方:

1. 設計を箇条書きで書き出す（どの状態をどこに持つか、どのロックが何を守るか、どの不変条件を
   誰が保証するか、失敗・並行・順序が入れ替わったときに何が起きるか）。
2. サブエージェントに設計文と関連コードを渡し、「**この設計が壊れる具体的な手順を挙げよ**。
   競合・順序・例外経路・途中で担当が交代する場合を疑え」と指示する（実装ではなく設計を
   攻撃させる）。
3. 返ってきた破れ方を設計へ反映してから実装に入る。潰さないと決めたものは doc コメントに残す。

当てはまらない issue（表示文言の修正、単純なバグ修正、設定項目の追加など）では**やらない**。
遅くなるだけで得るものが無い。

### 5. コミットする

実装が完了し検証が通ったら、変更内容を確認（`git status` / `git diff`）してからコミットする。

コミット前に **`docs/COMMIT.md` を読み**、**コミットのルールや記述内容**（メッセージの書式・
prefix・言語・issue 参照の書き方・署名の有無など）を確認し、それに従う。これはプロジェクトごとに
異なるコミット規約をカスタマイズするためのファイルであり、存在する場合は最優先で守る
（プロジェクトが規約の所有者であり、こちらが我流を持ち込まない）。

- `docs/COMMIT.md` がある場合: そこに書かれた規約を最優先で守る。
- `docs/COMMIT.md` が無い場合: 次に `docs/ISSUE.md`・`docs/rules/` にコミットに関する規約が
  ないか確認し、あればそれに従う。
- いずれにも規約が無い場合: 何を・なぜ変えたかが分かる簡潔なメッセージにし、
  **対象 issue を参照**する（例: メッセージ本文に `#42` を含める）。
- 変更が複数の論理単位にまたがる場合は、意味のある単位で分けてコミットしてよい。

### 6. 完了報告

作成したブランチ名、コミット（ハッシュとメッセージ）、実装で対応した内容と issue の
受け入れ条件の充足状況を簡潔に報告する。push や PR 作成が必要なら、それは次の作業として
案内する（このスキルでは行わない）。
