# za:cross-ship — issue を実装し、Claude と Codex のクロスレビューで仕上げる

GitHub issue を起点に、実装から「レビュー収束済みの PR」までを**途中の確認なしに**通しで
実行する。`za:ship` との違いは**レビューを 2 モデルで行うこと**だけ。

1. `za:fix-issue` — issue の実装とコミット
2. `za:pr` — PR の作成
3. **クロスレビュー・ループ** — Claude と Codex の両方でレビューし、指摘を修正して、
   **両方が「対応すべき新規指摘なし」になるまで**繰り返す（このスキル自身が回す）

狙いは、単一モデルのレビューに残る見落とし（同じモデルは同じ癖で見落とす）を、独立した
別モデルの目で埋めること。加えて、2 モデルが同じ箇所を指摘したかどうかを、指摘の
確度そのものとして使う。

マージは**行わない**（取り消しの効きにくい操作であり、最終確認はユーザーに残すため）。
完了時に `/za:merge` を案内する。

手順 1・2 は対応するスキルを **Skill ツールで順に呼び出して**実行する。各スキルの手順・
参照ドキュメント（`docs/rules/`・`docs/PR.md` など）はそのスキル自身の指示に従う。

## 手順

### 0. 前提を確認する（実装を始める前に 1 回）

Codex が使えないまま実装を進めると、最後にレビューできず全部やり直しになる。**着手前に**
次を確認する。

```sh
command -v codex          # 実行可能か
codex --version           # 版（--output-schema は 0.145.0 で確認済み）
codex login status        # 認証されているか
```

いずれかが満たせない場合は、**Claude 単独レビューへ黙って縮退させない**。このスキルの
価値は 2 モデルであることなので、停止して状況を報告し、`/za:ship`（Claude 単独）に
切り替えるかをユーザーに確認する。

### 1. 実装する（`za:fix-issue`）

`za:fix-issue` を呼び出し、issue の実装とコミットまで行う。

### 2. PR を作成する（`za:pr`）

`za:pr` を呼び出し、手順 1 のブランチ・コミットから PR を作成する。以降のレビューでは
ここで得た **PR 番号**を使う。

### 3. レビュー観点を読み込む

`docs/review-perspectives/` 配下の `*.md` を**すべて**読み込む。**この観点を Claude と
Codex の両方に同じものを渡す**（同じ基準で見せて、差が「モデルの違い」だけになるように
するため）。ディレクトリが無い場合は `za:review` の「デフォルトのレビュー観点」を使う。

### 4. 1 ラウンドのレビューを実行する（Claude と Codex を並行）

#### 4-a. Claude 側

`za:review` の手順 3 と同じ方法で行う。観点ごとにサブエージェントを 1 つ起動し、**すべて
並列で**実行する。各エージェントに渡すもの・返す指摘の形式も `za:review` と同じ
（`za:review` の SKILL.md を参照。形式をこのスキルで再定義はしない）。

#### 4-b. Codex 側

`codex exec` を非対話で 1 回呼び出す。プロンプト・観点・差分は**すべて stdin から渡す**。

```sh
SCHEMA="<このスキルの assets/codex-findings.schema.json の絶対パス>"
OUT="$(mktemp -t codex-review-XXXXXX).json"

{
  echo "あなたはコードレビュアーです。以下のレビュー観点だけに沿って、差分をレビューしてください。"
  echo "指摘は JSON スキーマに従って返してください。指摘が無ければ findings を空配列にしてください。"
  echo "差分だけで文脈が足りない場合は、リポジトリのファイルを読んで確認してかまいません。"
  echo "コードの修正は行わないでください（修正は別の担当が行います）。"
  echo
  echo "## レビュー観点"
  cat docs/review-perspectives/*.md
  echo
  echo "## すでに「対応しない」と判断済みの指摘（再度指摘しないでください）"
  echo "<前ラウンドで非対応と決めた指摘の一覧。初回は「なし」>"
  echo
  echo "## レビュー対象の差分"
  gh pr diff <PR番号>
} | codex exec -s read-only --color never \
      -c model_reasoning_effort="high" \
      --output-schema "$SCHEMA" \
      -o "$OUT" -

cat "$OUT"   # {"summary": "...", "findings": [...]}
```

各オプションの理由（すべて実機で確認済み）:

- `-s read-only` — レビューは読むだけ。**Codex にコードを書かせない**。修正は Claude が
  一手で行い、2 つのエージェントが同じ作業ツリーを書き換える競合を作らない。
- `-o <FILE>` — 最終メッセージ（JSON）をファイルへ書き出す。**stdout は使わない**
  （ヘッダやトークン数などのログが混ざるため）。
- `--output-schema <FILE>` — 指摘の形を固定し、Claude 側の指摘と機械的に突き合わせられる
  ようにする。スキーマは `assets/codex-findings.schema.json`。
- 末尾の `-` — プロンプトを stdin から読む。**引数で渡さない**（大きな差分で ARG_MAX に
  当たる。さらに非対話シェルでは stdin が勝手に取り込まれて意図しない入力が混ざるため、
  明示的に `-` で受けるのが安全）。
- `--color never` — ANSI エスケープを混ぜない。
- `-c model_reasoning_effort="high"` — 既定は `low`。レビューは推論を厚くするほど拾える。

呼び出しが失敗した場合は 1 回だけ再試行し、それでも失敗するなら手順 0 と同じ扱い
（停止して報告）にする。

### 5. 2 系統の指摘をマージする

Claude 側と Codex 側の指摘を 1 つの表に束ねる。同じ場所・同じ趣旨の指摘は 1 件に統合し、
**`検出元` を `claude` / `codex` / `both` として残す**。

判断のしかた:

- **`both`（両方が指摘）** — 独立した 2 モデルが同じものを見たので誤検知の確率が低い。
  優先して対応する。
- **片方だけの指摘** — 鵜呑みにしない。もう一方の視点で妥当性を確かめてから、対応/非対応を
  決める（片側モデルの誤検知をそのままコードに反映させないため）。妥当なら対応する。
- 対応/非対応の判断基準そのものは `za:review` の手順 4 と同じ。**非対応は理由を必ず記録**し、
  次ラウンドの Codex プロンプト（手順 4-b の「対応しないと判断済みの指摘」）と Claude 側の
  サブエージェントの両方に渡して、蒸し返しを防ぐ。

### 6. 修正してコミット・push する

**修正は Claude が行う**。`za:review` の手順 6 と同じ（コミット規約は `docs/rules/` 等に従い、
`git push` で PR の head ブランチへ反映する）。強制 push は行わない。

### 7. 収束するまで 4→6 を繰り返す

**収束条件: 同一ラウンドで Claude と Codex の両方が「対応すべき新規指摘なし」になること。**
片方だけ指摘なしはまだ収束ではない（もう一方の指摘を直せば、その修正自体が次のレビュー
対象になるため、必ず両方を再度通す）。

- すでに理由つきで「対応しない」と決めた指摘の再出は、収束の判定に数えない。
- 上限は **3 ラウンド**。超えても瑣末な指摘で往復が続く場合は打ち切り、残りを「対応しなかった
  指摘」として扱う。打ち切ったことと残件を報告に明記する（黙って切らない）。

### 8. 繰り返しそうな指摘をルール化する

`za:review` の手順 8 と同じく、今後も繰り返されそうな指摘を `docs/rules/{name}.md` へ
追記・修正する。

加えて、このスキル固有の作業として次を行う:

- **Codex だけが見つけた指摘**（`検出元` が `codex`）を洗い出す。これは
  `docs/review-perspectives/` の観点に穴があった、あるいは観点の記述が Claude 側に
  伝わりにくかった箇所である可能性が高い。該当する観点ファイルへ「何を見るか」を追記して、
  次回は Claude 側でも拾えるようにする。
- ルールや観点を更新した場合は、その変更も手順 6 のコミットに含める。

## ユーザー確認の扱い（このフローでの上書きルール）

呼び出す各スキルには「ユーザーに確認する」ステップがあるが、この通し実行では**確認のために
停止しない**。`za:ship` と同じルールで進める:

- **推奨案がある確認**（PR 作成の承認、実装方針の選択など）: 自分が推奨する案をそのまま
  採用して先へ進み、**判断ログ**に記録する。
- **推奨案を立てられる曖昧さ**: issue 本文・既存コード・プロジェクトのルールから最も整合する
  解釈を選んで進め、判断ログに「他にあり得た解釈」も添える。
- **レビューの指摘対応**: 対応する/しないの判断も自動で行い、非対応は理由つきでログに残す。

ただし次は**判断ではなく前提の不成立**なので、自動で進めず停止して報告する:

- `codex` が無い・未認証・レビュー呼び出しが再試行しても失敗する（手順 0 / 4-b）
- 指定された issue が見つからない・クローズ済み・引数が無い
- 作業ツリーに関係のない未コミット変更がある（混入を防ぐため）
- 現在のブランチがデフォルトブランチでなく、分岐元の判断がつかない
- push・PR 作成・CI などが失敗し、自動リトライで解消しない

## 判断ログ

通し実行中に自動採用した判断を、その場で記録して最後にまとめて出力する。形式は `za:ship`
と同じ:

```
## 自動採用した判断
| # | 場面 | 判断 | 理由 / 他にあり得た選択肢 |
|---|------|------|--------------------------|
| 1 | 実装方針 | 稼働時間は全置換APIにした | 既存の photo/work_location と同型のため。差分更新も可能だったが… |
| 2 | 指摘の採否 | codex 単独の「命名変更」指摘は非対応 | 既存コードの命名規約と衝突するため |
```

判断が一つも無ければ「自動採用した判断: なし」と報告する。ログは会話への出力のみで、
ファイルには残さない。

## 完了報告

最後に次をまとめて報告する:

- **成果物**: ブランチ名・コミット一覧・PR の URL とタイトル
- **クロスレビュー結果**: 対応した指摘 / 対応しなかった指摘（理由つき）を、**検出元
  （claude / codex / both）つきの一覧**で示す
- **ラウンド数と収束の有無**: 何周で収束したか。上限で打ち切った場合はその旨と残件
- **モデル別の傾向**: どちらがどんな指摘を拾ったか（1〜2 行）。観点ファイルへ反映した内容が
  あれば添える
- **自動採用した判断**: 上記の判断ログ
- **次の作業**: マージは `/za:merge <PR番号>` で行えることを案内する
