# 自動運転（オーケストレーション）の設定

`za:auto` がこのファイルを読んで動く。プロジェクト固有の値はすべてここに置き、スキル本体には
持たせない。**値を変えるときはこのファイルだけを直す。** 「任意」と書いた項目以外は必須で、
欠けていると `za:auto` は何もせずに止まる。

各表の値は例。自分のプロジェクトの表記に置き換える。

## ボード

| 項目 | 値 |
|---|---|
| owner | `{GitHub のユーザー名または org}` |
| project | `{プロジェクト番号}` |
| priority_field | `Priority`（任意。無ければ並び順にボードの手動順だけを使う） |

プロジェクト番号は `gh project list --owner <owner>` で確認する。

## Status の値

ボードの `Status` フィールドの選択肢名を、**ボード側の表記そのまま**（空白・大文字を含めて）書く。
`za:auto` の手順書に出てくる `Ready` などは、この表の役割名を指す。

| 役割 | 値 |
|---|---|
| backlog | `Backlog` |
| ready | `Ready` |
| in_progress | `In progress` |
| in_review | `In review` |
| done | `Done` |

## ラベル

リポジトリに実在するラベル名を書く（`gh label list` で確認。無ければ先に作る）。

| 役割 | ラベル名 | 意味 |
|---|---|---|
| needs_decision | `{要判断}` | 人間が決めることがある。`za:auto` は拾って、決める点を issue のコメントで尋ねて待つ |
| needs_human | `{要人手}`, `{要測定}`（任意） | 人の作業が成果物の一部。`za:auto` は拾って、機械にできるところまで進めてから、人の作業を issue のコメントで頼んで待つ |
| needs_manual_check | `{要実機確認}` | 実装は自動でできるが、マージ前に人間が実機で確かめる。`za:auto` は確認の手順を issue のコメントに書いて待つ |
| waiting | `{人待ち}` | **人の返事待ちの印。** `za:auto` が付け外しする。人はボードの `In progress` をこのラベルで絞り、自分の番の issue を見つける |

`needs_human` は複数書ける（`protected_paths` と同じく 1 つずつバッククォートで囲み、カンマ区切り）。
書かないプロジェクト（行ごと消すか、ラベル名を空にする。どちらも「設定なし」）では使わない。

**人が終えた合図はラベルではなく、issue へのコメント。** `za:auto` は待ちのコメント（`za:auto:waiting`）
より後に書かれた・書き直されたコメントを返事として読む。`waiting` のラベルを人が外しても、合図には
ならない。

## 依存の書式

issue 本文の `## 依存` 節に、**行頭 `- blocked by:` で 1 行 1 依存**を書く。`za:auto` は
この形の行だけを機械的に読む（他の書き方は依存として扱われず、警告として報告される）。

- 同じリポジトリ: `- blocked by: #123`
- 他のリポジトリ: `- blocked by: owner/repo#123`
- 依存なし: `- なし（すぐ着手可）`

行の末尾に補足（`（〜が決まってから）` など）を付けてよい。解決済みを示す取り消し線
（`~~blocked by: #123~~`）は依存として読まない。

## 昇格の条件

依存が解けた issue を `Backlog` から `Ready` に上げるときの追加条件。**`Backlog` は他の issue の
完了待ちだけに使う。** 未決定のことが書かれていても、`needs_decision` / `needs_human` のラベルが
付いていても、依存が解ければ上げる（決めること・人がやることは、着手したときに待ちとして人に回す）。

| 項目 | 値 | 意味 |
|---|---|---|
| require_milestone | `yes` | `yes` なら、マイルストーンが付いていない issue は昇格しない（スコープ外の扱い） |

## 上限と停止

**1 回の起動で処理する件数に上限は無い。** 進められるものが無くなるまで続ける。

| 項目 | 値 | 意味 |
|---|---|---|
| max_failures | `2` | 同じ issue の失敗（累計）がこの回数に達したら、何が起きたかを issue のコメントに書いて、人の判断を待つ |
| ci_timeout_minutes | `20` | CI の完了をこの時間まで待つ。超えたら `In review` のまま次の起動で再判定する |
| max_leftover_issues | `2` | 1 件のマージあたりに積み残しから作る issue の上限 |

人が実機確認や承認で「違う」と返したときの直し直しには、回数の上限は無い（人が返すかぎり直す）。

## 人に回すパス

PR の差分が次に触れていたら、`za:auto` はマージせず、承認を issue のコメントで頼んで待つ。
`za:auto` 自身が CI を通すために `test_paths` のファイルを変えたときも、承認を頼む。`docs/ORCHESTRATION.md` / `docs/MERGE.md` /
`.github/workflows/**` は常に含まれる（書かなくてよい）。

| 項目 | 値 | 意味 |
|---|---|---|
| protected_paths | `Makefile`, `.swiftlint.yml`, `scripts/ci/**` | CI が依存する検証手段。ここを変える PR は人が見る（テストを通すために検証を弱める経路を塞ぐ） |
| manual_check_paths | `Sources/App/UI/**`（任意） | ここに触れる PR は実機確認が要るとみなし、`za:auto` が `needs_manual_check` を付けて、確認を頼んで待つ |
| test_paths | `Tests/**`（任意） | ここに当たるファイルを削除する PR は人が見る |

PR 本文の確認事項（チェックボックス）はゲートに使われない。実機確認の要否はラベルと
`manual_check_paths` で決める。

## ゲート

マージの条件（CI 通過・レビュー収束・実機確認と承認が済んでいる・コンフリクトなし など）は
`za:auto` の手順 6 が正本で、設定では緩められない。CI は必須で、`.github/workflows/` に
ワークフローが無いリポジトリでは起動しない。マージ方法・base・head ブランチの扱いは
`docs/MERGE.md` に従う。

## 人間が見る場所

**ボードの `In progress` を `waiting` のラベルで絞る。** 出てくる issue が、人の返事待ち。

- 各 issue の最新の `za:auto:waiting` コメントに「お願いしたいこと」と「返し方」が書いてある。
  **その issue にコメントで返す。** 次に `za:auto` が起動したときに読まれ、続きが進む
  - 決めること（`decision`）: 選んだ案を返す
  - 人の作業（`human_task`）: 成果（デザインの URL と書き出した内容、測った値 など）を返す
  - ゲート（`gate`）: 実機確認の結果、承認するか、マージ方法など、頼まれたゲートごとに返す。
    「違う」と返せば `za:auto` が直して、もう一度頼む
  - リリース（`release`）: `/za:release` を走らせる。issue が閉じれば終わる
- **承認は GitHub の Approve ではなくコメントで返す**（`za:auto` は人と同じアカウントで PR を作るので、
  自分の PR を Approve できない）
- `za:auto` が残したコメント（本文の先頭が `<!-- za:auto:`）: 着手・収束・待ち・解決・失敗の記録。
  **返事は `za:auto` を動かしているアカウントで書く**（ほかのアカウントのコメントは読まない）

## 自動運転を止めたいとき

継続運転（cron や `/schedule` からの `claude -p "/za:auto"`、または `/loop`）を止める。
`za:auto` は自分でループの外側（次の起動）を止められない。実行中の 1 件は途中で止めず、その件の
報告まで待ってから止める。途中で止めてしまった場合も次の起動時に `za:auto` がボードと実態を
突き合わせて直すが、ローカルが作業ブランチに残っていれば手でデフォルトブランチに戻す必要がある。
