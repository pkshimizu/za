# za:release — リリース前チェックを通してから本番リリース

プロジェクトのリリースルール（`docs/RELEASE.md`）に従い、**リリース前チェックをすべて
通してからでないとリリース PR を作らない**。狙いは、リリース前にやるべきこと
（マイグレーションの本数確認、利用者向けマニュアルの更新、CI の確認など）を人の記憶に
頼らず機械で止めること。

`za:merge` が `docs/MERGE.md` を、`za:pr` が `docs/PR.md` を読むのと同じで、
**スキルは汎用・ルールはプロジェクト側**に置く。何をチェックするか・base / head・
PR の書式・マージ方法・デプロイの待ち方は、すべて `docs/RELEASE.md` が決める。

リリースは取り消しの効かない外部操作（PR 作成、マージ＝本番デプロイ）を含むので、
**PR 作成とマージのそれぞれで、ユーザーの承認を得てから実行する**（後述）。
下の手順を順番に実行する。

ユーザーに質問・確認を求めるときは、原則 `AskUserQuestion` で**選択式**（推奨できる案を
先頭の選択肢に置き、必要に応じて「おまかせ」などの選択肢を添える）で尋ねる。はい/いいえの
承認も含め、自由記述でしか答えられないものを除いて選択肢で提示する。

## 手順

### 1. リリースルールを読む

まず `docs/RELEASE.md` を読む。これはこのプロジェクトの**リリースルール**で、少なくとも
次が書かれている前提:

- base / head（リリース PR をどのブランチからどのブランチへ出すか）
- リリース PR のタイトル形式・本文に載せるもの・マージ方法
- **リリース前チェック**（上から順に実行する項目。各項目は「確認コマンド」と
  「通る条件」の対）
- （あれば）デプロイのワークフロー名、リリース後の確認

**`docs/RELEASE.md` が無い場合は止まる。** 「`docs/RELEASE.md` が無いためリリース前
チェックを行えません」と伝えて終了する。標準の書式やそれらしいチェックを勝手に補って
進めない。リリースは取り消しの効かない操作であり、ルール無しで走らせるのは、チェックを
すべて素通りさせるのと同じ。ファイルを用意する案内（何を書くべきか: 上の 4 点）だけ
添える。

読めるが上の前提を満たしていない（リリース前チェックの節が無い、チェックに確認コマンドが
無い等）場合も同様に止まり、何が足りないかを伝える。

### 2. リリース対象の差分を出す

`docs/RELEASE.md` の base / head（指定が無ければ `main` ← `develop`）で、今回リリースに
含まれる変更を把握する。

```sh
git fetch origin <base> <head>
git log --oneline origin/<base>..origin/<head>
git diff --stat origin/<base>...origin/<head>
```

- 差分が無い（head が base に取り込み済み）なら「リリースする変更がありません」と伝えて
  終了する。
- head ブランチが解決できない、`gh` が使えない、リポジトリが git でない場合も、
  推測で進めず状況を伝えて止まる。

差分の要約（含まれる PR の一覧、変更ファイルの傾向）は手順 4 の提示で使うので控えておく。

### 3. リリース前チェックを上から順にすべて実行する

`docs/RELEASE.md` の「リリース前チェック」を**書かれた順に、書かれたコマンドで**実行する。
コマンドを言い換えたり、手元の判断で省いたりしない（ルールの所有者はプロジェクト側）。

各チェックについて:

- 確認コマンドを実行し、出力を「通る条件」と突き合わせて **通った / 通らない** を判定する。
- 判定が人の判断を含む場合（「本数が不安でないこと」「`確認:` 行は人が見る」など）は、
  出力をそのまま示し、機械で決められる部分（本数、`NG:` の有無、終了コード）だけを
  機械で決め、残りは手順 4 の提示に載せて人に委ねる。
- チェックが**別ファイルを参照する**場合（対応表、ワークフロー定義など）、それが読めない・
  書式が崩れているなら、**「読めない」として止まる**。黙って素通りしない。
- コマンド自体が失敗した（終了コードがルールで定義された「通らない」ではなくエラー相当、
  `gh` の認証切れ、ブランチ未解決など）場合も「判定できない」として止まる。判定できない
  ことを「通った」に倒さない。

**1 つでも通らなければ、そこで止まる。** 残りのチェックは実行してもよいが（何が残って
いるかは分かった方が親切）、リリース PR は作らない。報告には次を含める:

- どのチェックで止まったか（番号・名前）と、確認コマンドの出力
- **何をすれば通るか**（`docs/RELEASE.md` に書かれた対処。例: 「`docs: マニュアルを
  リリース分に更新` の docs PR を先に `develop` へマージする」「`run-task` で先に
  マイグレーションを流す」）
- 通ったチェックの一覧（次回やり直すときに、どこから見ればよいか分かるように）

通らなかったチェックを、こちらで直して通す（マニュアルを書く、マイグレーションを流す等）
ことはしない。それぞれ別の作業・別の PR であり、リリースの流れの中で混ぜると
チェックの意味が無くなる。

### 4. リリース PR の内容を提示して承認を得る

すべてのチェックが通ったら、リリース PR の内容を組み立てて提示する。書式は
`docs/RELEASE.md` の指定に従う。最低限:

- タイトル（`docs/RELEASE.md` の形式。日付を含む形式なら今日の日付。同日の 2 回目以降の
  扱いが決まっていればそれに従う。既存のリリース PR を `gh pr list --search` で確認する）
- base ← head
- 含まれる変更（手順 2 の PR 一覧）
- 各チェックの結果（マイグレーションの本数、マニュアルの更新有無、CI の状態など。
  チェックが人の判断に委ねた出力—`確認:` 行など—は**ここに載せて**目に触れさせる）
- リリース後の確認があること（手順 7）

「この内容でリリース PR を作ってよいか」を確認する。**承認を得るまで PR は作らない。**
ユーザーが内容の修正を求めたら反映して再提示する。

### 5. リリース PR を作る

承認後、`gh pr create` で作成する。本文は一時ファイルに書いて `--body-file` で渡す
（複数行・Markdown をシェルのクォートで壊さないため）。

```sh
gh pr create --base <base> --head <head> --title "<タイトル>" --body-file <本文ファイル>
```

- 同じ base ← head のオープン PR が既にある場合は新規作成せず、その PR を使う
  （本文の更新が必要なら `gh pr edit`）。
- 作成に失敗した場合は、回避策を取らず失敗内容を報告して止まる。

### 6. 承認を得てからマージする

マージは**別途**承認を得る。PR 作成の承認をマージの承認と見なさない。base が保護されて
いない環境では、**この承認が本番反映の唯一のゲート**になる。

提示するのは:

- PR（番号・タイトル・URL）と base ← head
- PR 上のチェック・コンフリクトの状態
  （`gh pr view <番号> --json mergeable,mergeStateStatus,statusCheckRollup`）
- マージ方法と head ブランチを削除するか（`docs/RELEASE.md` の指定。指定が無ければ
  `za:merge` と同じく `docs/MERGE.md` → リポジトリの慣習の順で決める。リリース PR では
  head（`develop` 等）は**削除しないのが通常**なので、指定が無ければ削除しない）

承認後、`gh pr merge <番号> --merge`（方法は上で決めたものに置き換える）でマージする。
失敗したら回避策を取らず、失敗内容を報告して止まる。コンフリクトがあればこのスキルでは
解消しない。

### 7. デプロイを待って結果を報告する

`docs/RELEASE.md` にデプロイのワークフロー（名前・待ち方）が書かれていれば、それに従って
完了を待つ。書かれていなければ、base への push で走るワークフローを
`gh run list --branch <base> --limit 3` で探し、あれば待つ。無ければ「デプロイの
ワークフローは見つかりませんでした」と報告して次へ進む。

```sh
sleep 20   # マージ直後は run がまだ登録されていないことがある
ID=$(gh run list --workflow <ワークフロー> --branch <base> --limit 1 --json databaseId -q '.[0].databaseId')
gh run watch "$ID" --exit-status
gh run view "$ID"
```

- 各段階（ジョブ／ステップ）の結果を報告する。**途中で失敗した場合は、どこまで進んで
  どこで止まったかを明示する**（例: マイグレーションは success、デプロイは skipped）。
  中間状態（DB だけ進んでアプリが旧のまま等）の可能性があるなら、`docs/RELEASE.md` に
  ある復旧の案内を示す。このスキルでは復旧操作を勝手に行わない。

### 8. リリース後の確認

`docs/RELEASE.md` に「リリース後の確認」があれば、書かれた順に実行して結果を報告する
（ヘルスチェックの `curl`、ワークフローの各段階の確認など）。ブラウザでのログイン確認の
ように機械で行えないものは、その旨を伝えてユーザーに委ねる。

### 9. 完了報告

次を報告する:

- **リリース前チェック**: 各チェックの結果（通った／通らない、人に委ねた点）
- **リリース PR**: 番号・タイトル・URL・base ← head・含まれる変更
- **マージとデプロイ**: マージ方法、ワークフローの各段階の結果
- **リリース後の確認**: 実行した項目と結果、ユーザーに委ねた項目
- 途中で止まった場合は、**どこで止まり、何をすれば再開できるか**

## 補足

- このスキルは `docs/RELEASE.md` の**実行者**であって、ルールの所有者ではない。チェックの
  中身・順番・対処法はすべてプロジェクト側で決め、変えたいときは `docs/RELEASE.md` を
  直す。
- `docs/RELEASE.md` は `/za:init` の生成対象に**含めない**。base / head・CI のワークフロー
  名・確認コマンドはプロジェクトごとに異なり、ひな形のままでは「通る条件」が意味を持たず、
  形だけのチェックがリリースを通してしまう。プロジェクト側で実際のコマンドを実行して
  検証したものを書く（`docs/RELEASE.md` が無ければこのスキルは止まるので、書くまでは
  リリースできない、が正しい状態）。
