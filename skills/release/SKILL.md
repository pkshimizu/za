# za:release — リリース前チェックを通してから本番リリース

プロジェクトのリリースルール（`docs/RELEASE.md`）に従い、**リリース前チェックをすべて
通してからでないとリリース PR を作らない**。狙いは、リリース前にやるべきこと
（マイグレーションの本数確認、利用者向けマニュアルの更新、CI の確認など）を人の記憶に
頼らず機械で止めること。

`za:merge` が `docs/MERGE.md` を、`za:pr` が `docs/PR.md` を読むのと同じで、
**スキルは汎用・ルールはプロジェクト側**に置く。何をチェックするか・base / head・
PR の書式・マージ方法・デプロイの待ち方は、すべて `docs/RELEASE.md` が決める。このスキルは
その実行者であって所有者ではなく、チェックの中身を変えたいときは `docs/RELEASE.md` を直す。

リリースは取り消しの効かない外部操作（PR 作成、マージ＝本番デプロイ）を含むので、
**PR 作成とマージのそれぞれで、ユーザーの承認を得てから実行する**。この承認について:

- **他スキルの「確認なしで通す」ルールの対象外。** `za:goal` / `za:cross-goal` のような通し
  実行フローの中から呼ばれても、承認箇所では必ず停止する。
- **起動時のプロンプトや依頼文に「マージまでやって」と書かれていても、それを承認とは
  見なさない。** 承認は、内容を提示したあとに改めて取る。
- `za:pr` / `za:merge` にある「事前に確認不要と明示されていれば省いてよい」は**このスキル
  には適用しない**。
- 承認を取る手段が無い実行モード（非対話実行、サブエージェント経由など）では、リリース PR を
  作らずに「対話的に承認を得られないため中断」と報告して終了する。

下の手順を順番に実行する。

ユーザーに質問・確認を求めるときは、原則 `AskUserQuestion` で**選択式**（推奨できる案を
先頭の選択肢に置き、必要に応じて「おまかせ」などの選択肢を添える）で尋ねる。はい/いいえの
承認も含め、自由記述でしか答えられないものを除いて選択肢で提示する。

## 手順

### 1. リリースルールを読む

`docs/RELEASE.md` を読む。これはこのプロジェクトのリリースルールで、次の内容を期待する:

- 必須: **リリース前チェック**（上から順に実行する項目。各項目は「確認コマンド」と
  「通る条件」の対）
- 任意: base / head（無ければ `main` ← `develop`）、リリース PR のタイトル形式・本文に
  載せるもの・マージ方法、デプロイのワークフロー名、リリース後の確認

**読むのは作業ツリーのファイルではなく、リリースされる head 上の版**
（`git show origin/<head>:docs/RELEASE.md`）。現在のブランチが何であれ、head に取り込まれた
ルールで走るため（feature ブランチ上の未マージ版や、古いブランチに残った旧版で走らない）。
head は `docs/RELEASE.md` 自身が決めるので、次の順で解決する:

1. `git fetch origin` のうえ、作業ツリーに `docs/RELEASE.md` があればそれを読んで base / head
   を得る。無ければ既定の `main` ← `develop` を仮置きする。
2. `git show origin/<head>:docs/RELEASE.md` を読み、**以後はこの版を正とする**（base / head も
   この版で確定する）。作業ツリーの版と違っていれば、その旨を伝える。

**head 上に `docs/RELEASE.md` が無い場合は止まる。** 「`origin/<head>` に `docs/RELEASE.md` が
無いためリリース前チェックを行えません」と伝えて終了する。作業ツリーにはあるなら「先に head へ
取り込む」を、どこにも無いなら「ファイルに何を書くべきか（上の必須・任意の項目）」を案内する。
標準の書式やそれらしいチェックを勝手に補って進めない。リリースは取り消しの効かない操作であり、
ルール無しで走らせるのは、チェックをすべて素通りさせるのと同じ。

読めるが必須項目を満たしていない（リリース前チェックの節が無い、チェックに確認コマンドが
無い等）場合も同様に止まり、何が足りないかを伝える。

### 2. リリース対象の差分を出す

`docs/RELEASE.md` の base / head で、今回リリースに含まれる変更を把握する。

```sh
git fetch origin <base> <head>
git log --oneline origin/<base>..origin/<head>
git diff --stat origin/<base>...origin/<head>
git rev-parse origin/<head>     # チェックを通す head の SHA。手順 6 で照合する
```

- 差分が無い（head が base に取り込み済み）なら「リリースする変更がありません」と伝えて
  終了する。
- head ブランチが解決できない、`gh` が使えない、リポジトリが git でない場合も、
  推測で進めず状況を伝えて止まる。
- **差分に `docs/RELEASE.md` 自体の変更が含まれる場合**は、その diff
  （`git diff origin/<base>...origin/<head> -- docs/RELEASE.md`）を控えておき、手順 4 の
  提示に「ゲート自体の変更」として必ず載せる。リリース対象の変更がリリースのゲートを
  緩めていても、人の目に触れずに通ることがないようにするため。

差分の要約（含まれる PR の一覧、変更ファイルの傾向）は手順 4 の提示で使うので控えておく。

### 3. リリース前チェックを上から順にすべて実行する

`docs/RELEASE.md` の「リリース前チェック」を**書かれた順に、書かれたコマンドで**実行する。
コマンドを言い換えたり、手元の判断で省いたりしない。確認コマンドは読み取り専用である
前提（それは `docs/RELEASE.md` 側の責任）。読み取り専用と判断できないコマンドは、
実行前にその旨を伝えて確認する。

各チェックについて:

- 確認コマンドを実行し、出力を「通る条件」と突き合わせて **通った / 通らない** を判定する。
- **終了コードは、「通る条件」が終了コードで定義されているときだけ判定に使う。** 条件が
  出力の内容（本数、特定の行の有無など）で定義されているチェックでは、出力を条件に
  突き合わせて判定し、終了コードだけを理由に止めない（例: `grep -c` は該当 0 件で `0` を
  出力しつつ終了コード 1 を返す）。
- 判定が人の判断を含む場合（「本数が不安でないこと」、出力に目視で見る行が含まれる等）は、
  機械で決められる部分だけを機械で決め、残りの出力はそのまま手順 4 の提示に載せて
  人に委ねる。
- チェックが**別ファイルを参照する**場合（対応表、ワークフロー定義など）、それが読めない・
  書式が崩れているなら、**「読めない」として止まる**。黙って素通りしない。
- 確認コマンドはリポジトリ内のファイルを読むなら、`origin/<head>` 上の版を読む形
  （`git show origin/<head>:<path>` 等）で書かれていることを期待する（作業ツリーは head と
  一致しているとは限らない）。作業ツリーのファイルを直接読むコマンドは、作業ツリーが
  `origin/<head>` と一致している（`git rev-parse HEAD` が同じで、そのファイルに未コミット
  差分が無い）ときだけ実行し、そうでなければ「判定できない」として止まる。
- コマンド自体が実行できなかった（`gh` の認証切れ、ブランチ未解決、スクリプトの
  構文エラーなど）場合も「判定できない」として止まる。判定できないことを「通った」に
  倒さない。

**1 つでも通らなければ、そこで止まる。** 残りのチェックは実行してもよいが（何が残って
いるかは分かった方が親切）、リリース PR は作らない。報告には次を含める:

- どのチェックで止まったか（番号・名前）と、確認コマンドの出力
- **何をすれば通るか**（`docs/RELEASE.md` に書かれた対処。例: 前提となる別の PR を先に
  head へマージする、重い処理を先に手動で流す）
- 通ったチェックの一覧（次回やり直すときに、どこから見ればよいか分かるように）

通らなかったチェックを、こちらで直して通す（不足しているドキュメントを書く、処理を
先回りして流す等）ことはしない。それぞれ別の作業・別の PR であり、リリースの流れの中で
混ぜるとチェックの意味が無くなる。**ユーザーが「それでも進めて」と求めても、このスキルでは
リリース PR を作らない。** どうしても出す必要があるなら、`docs/RELEASE.md` のチェックを
直すか、手作業でリリースするよう案内して終了する（人の記憶に頼らず機械で止めることが、
このスキルの唯一の価値）。

### 4. リリース PR の内容を提示して承認を得る

すべてのチェックが通ったら、リリース PR の内容を組み立てて提示する。書式は
`docs/RELEASE.md` の指定に従う。最低限:

- タイトル（`docs/RELEASE.md` の形式。日付を含む形式なら今日の日付。同日 2 回目以降の
  扱いが決まっていれば、**マージ済みを含めて**既存のリリース PR を数える:
  `gh pr list --base <base> --state all --search "<タイトル> in:title"`。既定の
  `gh pr list` は open しか返さないので、`--state all` を忘れると同名の PR が作られる）
- base ← head
- 含まれる変更（手順 2 の PR 一覧）
- 各チェックの結果（機械で決めた判定と、人に委ねた出力）
- `docs/RELEASE.md` 自体の変更があれば、その diff（手順 2）
- リリース後の確認があること（手順 8）

「この内容でリリース PR を作ってよいか」を確認する。選択肢には少なくとも **作る / 内容を
直す / 止める** を置く。人に委ねたチェックを見て「止める」を選んだ場合は、手順 3 で止まる
ときと同じ形（どのチェックか・何をすれば通るか）で報告して終了する。**承認を得るまで PR は
作らない。** 内容の修正を求められたら反映して再提示する。

### 5. リリース PR を作る

承認後、`gh pr create` で作成する。本文は一時ファイルに書いて `--body-file` で渡す
（複数行・Markdown をシェルのクォートで壊さないため）。

```sh
gh pr create --base <base> --head <head> --title "<タイトル>" --body-file <本文ファイル>
```

- 同じ base ← head のオープン PR が既にある場合は新規作成しない。その PR の作成者・作成日時・
  現在の本文を提示し、承認された内容に `gh pr edit` で更新したうえで、その PR を使う
  （承認した内容と実際にマージされる PR を食い違わせない）。
- 作成に失敗した場合は、回避策を取らず失敗内容を報告して止まる。

### 6. 承認を得てからマージする

マージは**別途**承認を得る。PR 作成の承認をマージの承認と見なさない。base が保護されて
いない環境では、**この承認が本番反映の唯一のゲート**になる。

まず PR の状態を確認する
（`gh pr view <番号> --json headRefOid,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup`）:

- **`headRefOid` が手順 2 で控えた head の SHA と一致すること。** 異なれば、チェックを
  通したあとに head が進んでいる（他の PR が取り込まれた）ので、その差分はチェックを
  通っていない。手順 2 からやり直す。
- `mergeable` が衝突ありなら**マージしない**。解消が必要な旨を伝えて止まる（このスキルでは
  解消しない）。
- ステータスチェックに failure があれば**マージしない**。内容を伝えて止まる。pending なら
  完了するまで待つ。待てない事情があってもこのスキルでは pending のままマージしない
  （急ぐなら手作業でマージするよう案内して止まる）。
- レビュー承認の運用があれば（`reviewDecision`）、未承認・変更要求ありの場合はその旨を
  伝えて止まる。
- `--admin` など保護ルールやチェックを迂回するオプションは使わない。

問題が無ければ、次を提示して承認を得る:

- PR（番号・タイトル・URL）と base ← head（head の SHA を添える）
- チェック・コンフリクト・レビューの状態
- マージ方法と head ブランチを削除するか（`docs/RELEASE.md` の指定。指定が無ければ
  `za:merge` と同じく `docs/MERGE.md` → リポジトリの慣習の順で決める。リリース PR では
  head（`develop` 等）は**削除しないのが通常**なので、指定が無ければ削除しない）

承認後、head の SHA を結び付けてマージする（方法は上で決めたものに置き換える）:

```sh
gh pr merge <番号> --merge --match-head-commit <手順 2 の SHA>
```

状態確認からマージまでの間（pending 待ち、承認待ち）に head が進んでいれば、
`--match-head-commit` でマージが拒否される。その場合は「チェック後に head が進んだ」と
報告し、手順 2 からやり直す。それ以外の失敗も回避策を取らず、失敗内容を報告して止まる。

### 7. デプロイを待って結果を報告する

`docs/RELEASE.md` から取るのは**デプロイのワークフロー名**（と、あれば待ち時間の目安）
だけ。書かれていなければ、base への push で走るワークフローを
`gh run list --branch <base> --limit 3` で探し、あれば待つ。無ければ「デプロイの
ワークフローは見つかりませんでした」と報告して次へ進む。

**run の特定方法はこのスキル側で決める**（`docs/RELEASE.md` に別の待ち方が書かれていても
従わない）。待つ run は**今回のマージコミットのもの**に限る。`--branch <base> --limit 1` の
ように先頭 1 件で選ぶと、登録前なら前回リリースの run を掴んで「成功」と誤報告する。
`docs/RELEASE.md` の待ち方がその形なら、報告で修正を促す。

```sh
SHA=$(gh pr view <番号> --json mergeCommit -q .mergeCommit.oid)
ID=$(gh run list --workflow <ワークフロー> --commit "$SHA" --limit 1 --json databaseId -q '.[0].databaseId')
gh run watch "$ID" --exit-status
gh run view "$ID"
```

- マージ直後は run がまだ登録されていないことがある。`ID` が空なら少し待って数回
  やり直す（待ち方は環境の手段に従う。フォアグラウンドの `sleep` が使えない環境もある）。
  それでも特定できなければ「run を特定できなかった」と報告し、別の run の結果で代用しない。
- 各段階（ジョブ／ステップ）の結果を報告する。**途中で失敗した場合は、どこまで進んで
  どこで止まったかを明示する**（例: マイグレーションは success、デプロイは skipped）。
  中間状態（DB だけ進んでアプリが旧のまま等）の可能性があるなら、`docs/RELEASE.md` に
  ある復旧の案内を示す。このスキルでは復旧操作を勝手に行わない。

### 8. リリース後の確認

`docs/RELEASE.md` に「リリース後の確認」があれば、書かれた順に実行して結果を報告する
（ヘルスチェックの `curl`、ワークフローの各段階の確認など）。ブラウザでのログイン確認の
ように機械で行えないものは、その旨を伝えてユーザーに委ねる。

### 9. 完了報告

次を報告する:

- **リリース前チェック**: 各チェックの結果（通った／通らない、人に委ねた点）
- **リリース PR**: 番号・タイトル・URL・base ← head・含まれる変更
- **マージとデプロイ**: マージ方法、ワークフローの各段階の結果
- **リリース後の確認**: 実行した項目と結果、ユーザーに委ねた項目
- 途中で止まった場合は、**どこで止まり、何をすれば再開できるか**

## 補足

- `docs/RELEASE.md` は `/za:init` の生成対象に**含めない**。base / head・CI のワークフロー
  名・確認コマンドはプロジェクトごとに異なり、ひな形のままでは「通る条件」が意味を持たず、
  形だけのチェックがリリースを通してしまう。プロジェクト側で実際のコマンドを実行して
  検証したものを書く（`docs/RELEASE.md` が無ければこのスキルは止まるので、書くまでは
  リリースできない、が正しい状態）。
