# za:ship — issue を実装して PR・レビューまで通しで実行

GitHub issue を起点に、**専用の git worktree を用意したうえで**、次の 3 スキルをこの順で
**途中の確認なしに**通しで実行する。狙いは、issue 番号ひとつを渡せば「レビュー収束済みの
PR」まで無人で到達させ、ユーザーの待ち時間・往復回数を最小にすること。

0. **worktree の用意**（このスキル自身が行う。下記「作業場所」）
1. `za:fix-issue` — issue の実装とコミット
2. `za:pr` — PR の作成
3. `za:review` — 観点別の並列レビューと修正・push

マージは**行わない**（マージは取り消しの効きにくい操作であり、最終確認はユーザーに
残すため）。完了時に `/za:merge` を案内する。worktree の後片付けも `/za:merge` が行うので、
このスキルでは削除しない（PR がまだ開いており、追加修正の可能性があるため）。

## 作業場所（worktree）— 実装より先に必ず用意する

実装は**必ず専用の git worktree の中で行い、本体の作業ツリーでは作業しない**。

理由は並行 ship を可能にすること。1 つの作業ツリーは 1 ブランチしか持てないため、本体で
直接作業すると、2 本目の ship が同じツリーに別 issue の変更を混ぜてしまう。副次的に、
本体に未コミットの変更が残っていても ship を開始できるようになる。

なお worktree が分離するのは**ファイルの衝突だけ**である。同じファイルを触る issue を
並行させれば、後からマージする PR が必ずコンフリクトする。並行させる issue は、着手前に
想定変更ファイルが重ならないことを確認して選ぶ（重なるものは直列にする）。

### 0-1. issue を確認してブランチ名を決める

worktree の作成にブランチ名が要るので、先に `gh issue view <番号>` でタイトルを見て
`feature/{issue番号}-{slug}` を決める（`{slug}` の作り方は `za:fix-issue` の手順3と同じ）。
issue が見つからない・クローズ済みなら、ここで停止して報告する。

### 0-2. worktree を作って中に入る

`git fetch origin` で最新化してから、`EnterWorktree` ツールを
`name: "{issue番号}-{slug}"` で呼ぶ。`.claude/worktrees/` 配下に worktree が作られ、
セッションの作業ディレクトリがそこへ移る。分岐元は
`origin/{デフォルトブランチ}`（`worktree.baseRef` の既定 `fresh`）なので、`za:fix-issue` が
求める「最新のデフォルトブランチから分岐」を満たす。

**`EnterWorktree` が切るブランチ名は `worktree-{name}` になる**（`name` そのままではない）。
規約どおりの名前にするため、worktree に入った直後に改名する:

```sh
git branch -m feature/{issue番号}-{slug}
```

- 改名すると `ExitWorktree` の後片付けは元の `worktree-{name}` を探して失敗するため、
  ブランチだけ残ることがある。ship を中断して破棄する場合は `git branch -D` も実行する
  （正常フローでは `/za:merge` の `gh pr merge --delete-branch` が削除する）。
- `EnterWorktree` が使えない環境では
  `git worktree add <パス> -b feature/{issue番号}-{slug} origin/{デフォルトブランチ}` で
  作り、以降のコマンド・ファイル操作はそのパスを明示して実行する。
- 前のブランチに積む（スタックする）指示がユーザーからある場合だけ、分岐元をそのブランチに
  する。指示が無ければデフォルトブランチから分岐する。
- worktree は本体リポジトリの中（`.claude/worktrees/`）に作られる。`.claude` が gitignore
  されていないリポジトリでは、本体側に大量の未追跡ファイルとして現れてしまう。その場合は
  先に `.claude/worktrees/` を `.gitignore`（またはリポジトリを汚さない
  `.git/info/exclude`）へ追加してから進める。

### 0-3. gitignore されている作業必需品を worktree に用意する

**ここを飛ばすと ship が壊れる。** worktree には git 管理下のファイルしか無い。
`docs/rules/`・`docs/PR.md`・`docs/review-perspectives/` などの規約ドキュメントが
gitignore されているリポジトリでは、そのままだと後続スキルが規約を読めず、「ルールが
無いので既存コードの流儀で実装します」と言って我流の実装・PR・レビューになる。依存
パッケージが無ければ lint・型チェック・ビルドも動かない。

本体リポジトリのルートを基準に、次を worktree へ用意する（`git check-ignore -q <パス>` で
ignore されているものだけが対象。追跡済みのものは worktree に既にある）:

| 対象 | 例 | 方法 |
| --- | --- | --- |
| 規約・指示ドキュメント | `docs/`・`CLAUDE.md`・`AGENTS.md` | **symlink**（worktree 側での更新を本体へ反映するため。`za:review` の手順8はルールを更新する） |
| ローカル設定 | `.env`・`.env.local` 等 | symlink |
| 依存パッケージ | `node_modules/`・`vendor/bundle/`・`.venv/` | **コピー**（ビルドがキャッシュを書き込むので他の worktree と共有しない）。macOS/APFS は `cp -Rc`、Linux は `cp -R --reflink=auto` を使う。コピーオンライトなのでディスクはほぼ消費しない（400MB 程度で 30 秒前後。`npm ci` より速い） |

- `.claude/` を**丸ごと** symlink してはいけない。worktree 自身が `.claude/worktrees/` の
  下にあるため、自分を含む無限ループになる。必要なら `.claude/commands` のようにサブパス
  単位で張る。
- 用意し終えたら、`docs/` 配下の規約ファイルが worktree から実際に読めることを確認してから
  次へ進む（読めないまま進むと上記の我流モードに落ちる）。

### 0-4. lint・型チェック・ビルドが worktree で通ることを確認する

実装を始める前に、プロジェクトの検証コマンド（`npm run lint`・`npm run typecheck` 等）を
worktree で一度走らせ、**環境として動くこと**を確かめる。既存のエラーが出るのは構わない
（それは issue 側の話）。ここで見るのは「ツールが起動して最後まで走るか」。

worktree は本体リポジトリの中に作られるため、**設定ファイルを上位ディレクトリへ探しに行く
ツールが、本体側の設定まで拾って壊れる**ことがある。実例として ESLint（レガシー設定）は、
`.eslintrc` に `"root": true` が無いと worktree と本体の両方の設定を読み込み、
`ESLint couldn't determine the plugin "@typescript-eslint" uniquely.` で起動に失敗する。

- この種の失敗が出たら、設定に探索の打ち切り（ESLint なら `"root": true`）を足して直す。
  これはプロジェクト本体への修正になるので、判断ログに残し、可能なら今回のブランチに
  含めず別途扱う。
- 直せない場合は、worktree を本体の外
  （`git worktree add ../{リポジトリ名}-{issue番号} ...`）に作り直して上位探索を避ける。

## 実行方法

各ステップは対応するスキルを **Skill ツールで順に呼び出して**実行する
（`za:fix-issue` → `za:pr` → `za:review`）。各スキルの手順・参照ドキュメント
（`docs/rules/`・`docs/PR.md`・`docs/review-perspectives/` など）はそのスキル自身の
指示に従う。この通しフローが上書きするのは「ユーザー確認の扱い」（下記）と、worktree で
作業することに伴う次の 2 点だけ。

- `za:fix-issue` の**手順3（作業ブランチの作成）は実施させない**。ブランチは手順 0-2 の
  worktree 作成時に切れており、二重に切ると分岐元がずれる。スキル呼び出しの引数で
  「ブランチは `feature/{issue番号}-{slug}` で作成済み・チェックアウト済みなので手順3は
  スキップし、手順4の実装から始めること」と明示して渡す。
- `za:pr` に渡す変更内容は手順 1 の結果（ブランチ・コミット）から拾う。
- `za:review` に渡す PR 番号は手順 2 で作成した PR の番号を使う。`za:review` の手順1に
  ある `gh pr checkout` も**実施させない**（すでに worktree で当該ブランチにいるため。
  本体ツリーで checkout すると worktree と競合する）。

## ユーザー確認の扱い（このフローでの上書きルール）

各スキルの手順には「ユーザーに確認する」「承認を得る」というステップがあるが、
この通し実行では**確認のために停止しない**。代わりに次のルールで進める:

- **推奨案がある確認**（PR 作成の承認、実装方針の選択など）: 自分が推奨する案を
  そのまま採用して先へ進む。何をどう判断したかを**判断ログ**（下記）に記録する。
- **推奨案を立てられる曖昧さ**（issue の記述が曖昧、複数の妥当な実装がある等）:
  issue 本文・既存コード・プロジェクトのルールから最も整合する解釈を選んで進め、
  判断ログに「他にあり得た解釈」も添える。ユーザーは最後のログを見て、ずれていれば
  修正を指示できる。
- **レビューの指摘対応**: `za:review` の「対応する/しない」の判断も自動で行い、
  対応しなかった指摘は理由つきでログに残す（これは za:review 自体のサマリーと同じ）。

ただし、次の状況は**判断ではなく前提の不成立**なので、自動で進めず停止して報告する:

- 指定された issue が見つからない・クローズ済み・引数が無い
- worktree の作成に失敗する（同名ブランチが既にある、既に別の worktree セッション中 等）
- 手順 0-3 の用意ができない（規約ドキュメントが worktree から読めない、依存パッケージを
  用意できない）。規約を読めないまま実装すると我流の成果物になるため、必ず止める
- push・PR 作成・CI などが失敗し、自動リトライで解消しない

逆に、**本体の作業ツリーに未コミットの変更があっても停止しない**。worktree で作業するので
混入しない（ただし、その変更が今回の issue に関係しそうなら判断ログに残す）。

これらは推測で進めると取り返しのつかない混入や誤実装につながるため、確認省略の
対象にしない。

## 判断ログ

通し実行中に自動採用した判断を、その場で記録して最後にまとめて出力する。形式:

```
## 自動採用した判断
| # | 場面 | 判断 | 理由 / 他にあり得た選択肢 |
|---|------|------|--------------------------|
| 1 | 実装方針 | 稼働時間は全置換APIにした | 既存の photo/work_location と同型のため。差分更新も可能だったが… |
| 2 | PR 作成 | 承認確認を省略して作成 | 通し実行の方針どおり |
```

判断が一つも無ければ「自動採用した判断: なし」と報告する。ログは会話への出力のみで、
ファイルには残さない（PR・コミットに履歴は残るため）。

## 完了報告

最後に次をまとめて報告する:

- **成果物**: ブランチ名・コミット一覧・PR の URL とタイトル
- **作業場所**: 作成した worktree のパス（セッションは worktree の中にいる旨も添える）
- **レビュー結果**: 対応した指摘 / 対応しなかった指摘（理由つき）のサマリー
  （za:review のサマリーを流用してよい）
- **自動採用した判断**: 上記の判断ログ
- **次の作業**: マージは `/za:merge <PR番号>` で行えること、worktree の削除もそこで
  まとめて行われることを案内する
