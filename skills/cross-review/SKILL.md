# za:cross-review — PR を Claude と Codex の 2 モデルでレビューして修正

GitHub プルリクエスト（PR）を **Claude と Codex の 2 モデル**でレビューし、出た指摘を修正して、
**両方が「対応すべき新規指摘なし」になるまで**繰り返す。`za:review` の 2 モデル版。

狙いは、単一モデルのレビューに残る見落とし（同じモデルは同じ癖で見落とす）を、独立した
別モデルの目で埋めること。加えて、2 モデルが同じ箇所を指摘したかどうかを、指摘の確度
そのものとして使う。

下の手順を順番に実行する。修正をコミットしたら、**リモートへ push する**（PR に追従させる）。

## ホストと相手側

このスキルは Claude Code と Codex のどちらからでも実行される。役割は次のとおり。

- **ホスト** — いまこのスキルを実行しているエージェント自身（Claude Code なら Claude、
  Codex なら Codex）。レビューだけでなく、**指摘の採否判断とコードの修正・コミットを担う**。
- **相手側** — もう一方のモデル。CLI を 1 回呼び出してレビューだけさせる
  （Claude Code から見た相手側は `codex exec`、Codex から見た相手側は `claude -p`）。

**修正はホストだけが行う**。相手側は常に読み取り専用で呼ぶ。2 つのエージェントが同じ作業
ツリーを書き換える競合を作らないため。

## 手順

### 1. 対象 PR を特定してチェックアウトする

`za:review` の手順 1 と同じ。引数の PR 番号/URL（例: `/za:cross-review 42`）から特定し、
`gh pr view` / `gh pr diff` で内容と差分を把握し、`gh pr checkout <番号>` で取り出す。

- 引数が無い場合は `gh pr list` を提示して確認する。
- PR が見つからない／クローズ済み、`gh` が使えない場合は、推測で進めず状況を伝えて確認する。
- 呼び出し元スキル（`za:cross-goal` など）から PR 番号を渡された場合はそれを使う。

### 2. レビュー体制を決める（縮退の判断）

相手側の CLI が使えるかを確認する。相手側が Codex なら:

```sh
command -v codex          # 実行可能か
codex --version           # 版（--output-schema は 0.145.0 で確認済み）
codex login status        # 認証されているか
```

相手側が Claude なら:

```sh
command -v claude         # 実行可能か
claude --version          # 版
claude auth status        # JSON。loggedIn が true か
```

判定は次のとおり。

- **相手側が使える** → クロスレビュー（2 モデル）で進む。
- **相手側が使えない**（未インストール・未認証・後述の呼び出し失敗）→ **自己レビューに縮退して
  処理を続ける**。ただし**黙って縮退しない**。何が使えないのか（未インストール／未認証／
  呼び出し失敗のどれか）と、以降はホスト単独のレビューになることを**その場でユーザーに伝えて
  から**続行する。縮退の可否をユーザーに確認して止まる必要はない（レビュー自体は成立するため）。
- ホスト自身は必ず使える（それが動いてこのスキルを実行している）。したがって「どちらも
  使えない」状態は起こらない。

縮退したかどうかは、手順 9 の完了報告にも必ず明記する。

### 3. レビュー観点を読み込む

`docs/review-perspectives/` 配下の `*.md` を**すべて**読み込む。**同じ観点をホストと相手側の
両方に渡す**（同じ基準で見せて、差が「モデルの違い」だけになるようにするため）。
ディレクトリが無い場合は `za:review` の「デフォルトのレビュー観点」を使う。

### 4. 1 ラウンドのレビューを実行する（ホストと相手側を並行）

**4-a と 4-b は必ず同時に走らせる**。どちらも読み取り専用なので競合はせず、直列に回すと
1 ラウンドの待ち時間が単純に 2 倍になる。具体的には次のようにする。

- **Claude がホストの場合** — 4-a のサブエージェント起動と 4-b の `codex exec`（Bash）を
  **同一メッセージ内でまとめて発行する**。長く待たせたくない場合は Bash 側を
  `run_in_background` で投げ、サブエージェントの結果を待つ間に進行させてもよい。
- **Codex がホストの場合** — 4-b の `claude -p` を**先にバックグラウンドで起動**し
  （末尾に `&`、または `nohup … &` で PID を控える）、その間に 4-a の観点別レビューを自分で
  進める。両方終わってから手順 5 へ進む。

```sh
# Codex がホストの場合の例: 相手側を先に投げてから自分のレビューを始める
{ … } | claude -p … > "$OUT" 2>"$ERR" &
CLAUDE_PID=$!
# ここで 4-a（自分の観点別レビュー）を進める
wait "$CLAUDE_PID"; echo "exit=$?"
```

#### 4-a. ホスト側

- **Claude がホストの場合** — `za:review` の手順 3 と同じ。観点ごとにサブエージェントを
  1 つ起動し、**すべて並列で**実行する。各エージェントに渡すもの・返す指摘の形式も
  `za:review` と同じ（形式をこのスキルで再定義はしない）。
- **Codex がホストの場合** — 並列サブエージェントが無いので、**観点を 1 つずつ順に**レビュー
  する（複数の観点を一度に混ぜない。1 つの視点に集中させるほど深く見られるため）。

#### 4-b. 相手側（手順 2 で縮退した場合はスキップ）

いずれの場合も、プロンプト・観点・差分は**すべて stdin から渡す**。

**相手側が Codex のとき**（Claude Code で実行中）:

```sh
SCHEMA="<このスキルの assets/findings.schema.json の絶対パス>"
OUT="$(mktemp -t codex-review-XXXXXX).json"

{
  echo "あなたはコードレビュアーです。以下のレビュー観点だけに沿って、差分をレビューしてください。"
  echo "指摘は JSON スキーマに従って返してください。指摘が無ければ findings を空配列にしてください。"
  echo "差分だけで文脈が足りない場合は、リポジトリのファイルを読んで確認してかまいません。"
  echo "コードの修正は行わないでください（修正は別の担当が行います）。"
  echo
  echo "## レビュー観点"
  cat docs/review-perspectives/*.md
  echo
  echo "## すでに「対応しない」と判断済みの指摘（再度指摘しないでください）"
  echo "<前ラウンドで非対応と決めた指摘の一覧。初回は「なし」>"
  echo
  echo "## レビュー対象の差分"
  gh pr diff <PR番号>
} | codex exec -s read-only --color never \
      -c model_reasoning_effort="high" \
      --output-schema "$SCHEMA" \
      -o "$OUT" -

cat "$OUT"   # {"summary": "...", "findings": [...]}
```

各オプションの理由（すべて実機で確認済み）:

- `-s read-only` — レビューは読むだけ。**相手側にコードを書かせない**。
- `-o <FILE>` — 最終メッセージ（JSON）をファイルへ書き出す。**stdout は使わない**
  （ヘッダやトークン数などのログが混ざるため）。
- `--output-schema <FILE>` — 指摘の形を固定し、ホスト側の指摘と機械的に突き合わせられる
  ようにする。スキーマは `assets/findings.schema.json`（**ファイルパス**で渡す）。
- 末尾の `-` — プロンプトを stdin から読む。**引数で渡さない**（大きな差分で ARG_MAX に
  当たる。さらに非対話シェルでは stdin が勝手に取り込まれて意図しない入力が混ざるため、
  明示的に `-` で受けるのが安全）。
- `--color never` — ANSI エスケープを混ぜない。
- `-c model_reasoning_effort="high"` — 既定は `low`。レビューは推論を厚くするほど拾える。

**相手側が Claude のとき**（Codex で実行中）:

```sh
SCHEMA="<このスキルの assets/findings.schema.json の絶対パス>"
OUT="$(mktemp -t claude-review-XXXXXX).json"

{
  # プロンプトの中身は Codex 版と同じ（観点・非対応済みの指摘・差分）
  ...
} | claude -p --model opus --effort high \
      --output-format json --json-schema "$(cat "$SCHEMA")" \
      --tools "Read,Grep,Glob" --permission-mode dontAsk > "$OUT"

jq -c '.structured_output' "$OUT"   # {"summary": "...", "findings": [...]}
```

各オプションの理由（すべて実機で確認済み）:

- `-p` — 非対話（print モード）。プロンプトは stdin から渡す（Codex 版と同じ理由）。
- `--tools "Read,Grep,Glob"` — 読み取り専用のツールだけを渡す。`Edit` / `Write` / `Bash` を
  渡さないことで、**相手側にコードを書かせない**（Codex 側の `-s read-only` に相当）。
- `--permission-mode dontAsk` — 非対話では許可を尋ねられても答えられない。尋ねずに進めさせる。
- `--json-schema` — 指摘の形を固定する。Codex の `--output-schema` と違い、**ファイルパスでは
  なく JSON 文字列**を受けるので `"$(cat "$SCHEMA")"` で渡す。
- `--output-format json` — 検証済みのオブジェクトは `.structured_output` に入る
  （`.result` にも同じ内容が JSON 文字列で入る）。実行ログやコストが同じ JSON に混ざるので、
  **必ず `.structured_output` を取り出す**。
- `--model opus --effort high` — レビューは推論を厚くするほど拾える。

呼び出しが失敗した場合（非 0 終了、`.is_error` が true、JSON が壊れている等）は 1 回だけ
再試行し、それでも失敗するなら**手順 2 の縮退と同じ扱い**にする。すなわち、失敗した事実を
ユーザーに伝えてから、そのラウンド以降はホスト単独の自己レビューで続行する（停止しない）。

### 5. 2 系統の指摘をマージする

ホスト側と相手側の指摘を 1 つの表に束ねる。同じ場所・同じ趣旨の指摘は 1 件に統合し、
**`検出元` を `claude` / `codex` / `both` として残す**（モデル名で残す。ホスト／相手側という
相対的な呼び方では、後から読んだときにどちらのモデルが拾ったのか分からなくなるため）。

判断のしかた:

- **`both`（両方が指摘）** — 独立した 2 モデルが同じものを見たので誤検知の確率が低い。
  優先して対応する。
- **片方だけの指摘** — 鵜呑みにしない。もう一方の視点で妥当性を確かめてから、対応/非対応を
  決める（片側モデルの誤検知をそのままコードに反映させないため）。妥当なら対応する。
- 対応/非対応の判断基準そのものは `za:review` の手順 4 と同じ。**非対応は理由を必ず記録**し、
  次ラウンドの相手側プロンプト（手順 4-b の「対応しないと判断済みの指摘」）とホスト側の
  レビューの両方に渡して、蒸し返しを防ぐ。

**自己レビューに縮退している場合**は検出元が 1 つしか無いので、`both` による確度の裏取りは
使えない。その分、指摘を採用する前にホスト自身で根拠を確かめる（`za:review` と同じ扱い）。

### 6. 修正してコミット・push する

**修正はホストが行う**。`za:review` の手順 6 と同じ（コミット規約は `docs/rules/` 等に従い、
`git push` で PR の head ブランチへ反映する）。強制 push は行わない。

### 7. 収束するまで 4→6 を繰り返す

**収束条件: 同一ラウンドで両モデルが「対応すべき新規指摘なし」になること。**
片方だけ指摘なしはまだ収束ではない（もう一方の指摘を直せば、その修正自体が次のレビュー
対象になるため、必ず両方を再度通す）。自己レビューに縮退している場合は、ホスト側が新規指摘
なしになった時点で収束とする。

- すでに理由つきで「対応しない」と決めた指摘の再出は、収束の判定に数えない。
- 上限は **3 ラウンド**。超えても瑣末な指摘で往復が続く場合は打ち切り、残りを「対応しなかった
  指摘」として扱う。打ち切ったことと残件を報告に明記する（黙って切らない）。

### 8. 繰り返しそうな指摘をルール化する

`za:review` の手順 8 と同じく、今後も繰り返されそうな指摘を `docs/rules/{name}.md` へ
追記・修正する。

加えて、このスキル固有の作業として次を行う:

- **相手側だけが見つけた指摘**を洗い出す。これは `docs/review-perspectives/` の観点に穴が
  あった、あるいは観点の記述がホスト側に伝わりにくかった箇所である可能性が高い。該当する
  観点ファイルへ「何を見るか」を追記して、次回はホスト側でも拾えるようにする。
- ルールや観点を更新した場合は、その変更も手順 6 のコミットに含める。

### 9. 完了報告

次をまとめて報告する:

- **レビュー体制**: クロスレビュー（claude + codex）か、自己レビューに縮退したか。
  縮退した場合は**何が使えなかったのか**（未インストール／未認証／呼び出し失敗）も添える。
- **修正内容のサマリー**: 何を直したか（ファイル単位の要点）
- **対応した指摘 / 対応しなかった指摘**（理由つき）を、**検出元（claude / codex / both）つきの
  一覧**で示す
- **ラウンド数と収束の有無**: 何周で収束したか。上限で打ち切った場合はその旨と残件
- **モデル別の傾向**: どちらがどんな指摘を拾ったか（1〜2 行）。観点ファイルへ反映した内容が
  あれば添える
- **push 結果**: コミットして push したブランチ（PR への反映）

## 指摘の形式

ホスト側の指摘の形式は `za:review` の「指摘の形式」と同じ。相手側 CLI から受け取る指摘は
`assets/findings.schema.json` で構造化する（`za:review` の形式と同じ項目を JSON にしたもの）。
両者を機械的に突き合わせられるようにするための取り決めなので、片方だけ形を変えない。
